# EZSL.js — Online Playground (v1.0.x)

Internal design doc for the v1.0.x Ecosystem Launch "Online Playground (browser-based editor + live preview, shareable shader URLs)" deliverable. Read `docs/architecture/dev-server.md` first — the Playground's hot-reload/error-handling model deliberately mirrors `ezsl dev`'s own (`swapProgram`-based live updates, an error overlay that leaves the previous frame rendering rather than blanking the canvas), applied to a browser-native editor instead of a file-watching Node server.

## Scope: three of three roadmap sub-items, with "community/moderated" explicitly out of scope

- **Real-time transpile-and-compile feedback loop** — done.
- **Split view: EZSL source ↔ generated GLSL output** — done.
- **Shader gallery** — done, in a deliberately narrowed form: a **static, curated** gallery (`src/gallery.ts`), not a **community/submission** gallery. Per an explicit follow-up user decision, the roadmap's "shader gallery / community gallery (moderated submissions)" wording was split into its two real halves: a gallery (a browsable, selectable list of shaders inside the Playground) is buildable and was built; a *community submission* mechanism with *moderation* needs a real backend to store submissions and an ongoing human moderation commitment to review them before they're publicly visible — neither is something a single automated pass can responsibly stand up, moderation specifically being an ongoing human commitment, not a one-time build task. That half remains explicitly out of scope — see "The gallery: curated, not community-submitted" below for exactly what was built instead and why it still satisfies the spirit of "a gallery."

## Architecture: fully static, zero backend

The entire Playground — editor, compiler, WebGL2 preview, and shareable-URL mechanism — runs client-side, with no server component beyond serving static files (Vite's dev server locally; any static host, including GitHub Pages, in production). This is possible because of two things already true about EZSL.js before this milestone: the whole compiler (`compileEzsl`) already runs entirely in the browser (no server-side compilation step exists anywhere in the project), and a shareable-URL mechanism that encodes the shader directly into the URL's **fragment** (`#shader=<base64>`) needs no server at all — the fragment portion of a URL is never sent in an HTTP request (only available to client-side JavaScript via `location.hash`), so "sharing a shader" is really just "sharing a URL," no storage required.

## Editor: CodeMirror 6 (explicit user decision)

Considered against Monaco (VS Code's own editor) and a plain `<textarea>`. Monaco was rejected specifically for its weight (~2-5MB) and web-worker setup complexity — this project has consistently avoided heavy dependencies where a lighter option suffices (the CLI's hand-written argv parsing, the dev server's zero-dependency `node:http` server, the VS Code extension's esbuild-bundled minimal footprint). A plain textarea was rejected as too weak an editing experience for what's meant to be the project's most visible, try-it-now entry point. CodeMirror 6 was chosen as the middle ground: a few hundred KB, no worker requirement, and — since EZSL syntax has no dedicated CodeMirror language mode — `@codemirror/lang-cpp`'s C-like highlighting is used as a reasonable approximation (EZSL and GLSL share enough surface syntax — brace blocks, `//` comments, C-style operators — that C-family highlighting reads correctly for the common case, even though it doesn't know EZSL's specific keywords like `array`/`fn`/`struct`).

## Real-time compile loop and hot-swap (mirrors `ezsl dev`)

Every editor keystroke schedules a debounced (150ms) recompile — fast enough to feel real-time (the roadmap's own wording) without recompiling on every single keystroke of a fast typist. `recompile()` (`src/main.ts`) does the same three things `ezsl dev`'s client script does (see `docs/architecture/dev-server.md`):

1. Compile via `compileEzsl` — a `LexError`/`ParseError`/`CompileError` shows a formatted overlay (source snippet + caret, via a locally-reimplemented `formatEzslError` — see below) and **stops there**, leaving both the GLSL panel and the WebGL preview showing their last-successful state rather than going blank.
2. On success, update the GLSL split-view panel with `generateFragmentShaderMapped`'s real output.
3. Mount (first successful compile) or **hot-swap** (`EzslRuntimeHandle.swapProgram`, every later one) the WebGL2 preview — deliberately not destroy-and-remount on every edit, for the exact reason `ezsl dev` avoids it: repeatedly acquiring a new WebGL2 context on the same canvas risks exhausting the browser's limited live-context budget over a long editing session, and would restart the `time` uniform to `0` on every keystroke.

## `formatEzslError`: a local reimplementation, not a shared export

`src/cli/formatCliError.ts` (in the main `ezsl` package) already formats a `LexError`/`ParseError`/`CompileError` as a source-snippet-plus-caret block — but it's an internal CLI module, never re-exported from `src/index.ts` (the package's frozen public surface — see `docs/API_STABILITY.md`). Rather than either (a) exporting an internal CLI formatter as new public API purely to serve this one other consumer, or (b) leaving Playground errors unformatted, `ezsl-playground/src/formatError.ts` reimplements the same visual shape locally, using only the already-public `LexError`/`ParseError`/`CompileError` classes' own `.line`/`.column`/`.message` fields. This is a small, deliberate duplication — not a shared-code opportunity missed, since sharing it would mean adding a new export to the frozen public API for a formatting concern that's arguably CLI/tooling-specific, not core library API.

## Shareable URLs: base64, not compressed (explicit user decision)

`urlState.ts` encodes the shader source as `encodeURIComponent` + `btoa`, decoded via the inverse (`atob` + `decodeURIComponent`) — the standard workaround for `btoa`'s Latin1-only limitation, since raw `btoa` on a UTF-8 string with any non-Latin1 character throws. A compressed encoding (via the browser's native `CompressionStream` API) was considered and rejected: real EZSL shaders are typically 1-20 lines (per every example in the main `examples/` directory), so uncompressed base64 keeps URLs a reasonable length for the overwhelming majority of real shaders, and avoiding compression avoids an async encode/decode step and a fallback path for browsers without `CompressionStream` support — a meaningful simplicity win for a marginal length benefit on typical inputs. The URL updates live via `history.replaceState` (not `pushState`) as the user types, specifically so every keystroke doesn't spam a new browser-history entry — only the final state before navigating away is what ends up shareable via the browser's own "copy link" affordances, and the explicit "Copy Share Link" button always builds a fresh, correct URL regardless.

## The gallery: curated, not community-submitted

`src/gallery.ts` is a static, build-time list of 21 already-validated `.ezsl` sources, imported directly from the main repo's `examples/` directory via Vite's `?raw` import — the same mechanism every example's own `main.ts` (and the cross-browser integration harness, `examples/_harness/main.ts`) already uses. Every entry is a shader `npm run test:integration` (in the main repo) has already confirmed compiles, links, and renders correctly across Chromium, Firefox, WebKit, and Edge — the gallery reuses that existing validation rather than re-establishing it for a second time.

**Not every example qualifies.** Only a `shader.ezsl` compiled via a bare `compileEzsl(source)` call fits the Playground's own `recompile()` function (see above) — it has no way to pass `customFunctions` or a multi-pass `bufferNames` graph. Excluded, and documented as excluded directly in `gallery.ts`'s own comment: `multi-pass`/`three-integration`/`canvas2d-interop` (structurally different — no single `shader.ezsl` file at all), `escape-hatch`/`type-system` (need `customFunctions` registered), and `error-demo`/`did-you-mean-demo` (deliberately broken, meant to demonstrate a compile failure, not to render).

The UI is a collapsible left-hand panel (`#gallery-panel`, toggled via a header button) listing each entry by name; clicking one replaces the editor's entire document (via a single CodeMirror `dispatch()` call) rather than calling `recompile()` directly — this keeps exactly one code path (the editor's own `updateListener`) responsible for reacting to *any* content change, whether it came from typing or a gallery click, so the debounced-recompile/URL-update/active-item-highlight logic can't drift between the two triggers. The currently-loaded gallery entry (if the editor's content exactly matches one) is highlighted, updated on every recompile — including when the *content itself* happens to match a gallery entry after manual edits, not just right after a click.

## Validation

Two layers, following the project's established "prove it in a real browser, not just unit tests" standard for anything runtime-facing:

1. **`tests/urlState.test.ts`** (5 Jest cases) — the pure encode/decode logic (round-tripping ASCII, multi-line, Unicode, and empty-string shaders; confirming the output is base64-safe), run under Node directly since `btoa`/`atob` are globally available there (no jsdom/polyfill needed).
2. **`tests/playground.integration.mjs`** (`npm run test:integration`, a real Playwright/Chromium session against a real running Vite dev server, mirroring the main repo's `tests/integration/run.mjs` pattern) — confirms, in a real browser: the initial page load populates the GLSL split-view with real GLSL; the gallery renders all 21 curated entries; clicking one loads its real, multi-line source into the editor (checked via CodeMirror's own rendered line count and first-line content, not the DOM's flattened `textContent`, which drops inter-line newlines — a real gotcha caught while writing this check, see below), recompiles it, and marks it active; the gallery panel actually collapses to zero width when toggled; editing the source live-updates the GLSL panel; a genuine `CompileError` (an unknown-function call) produces a correctly formatted overlay; fixing the shader hides the overlay again; the URL fragment updates live to reflect the current shader; and — the actual "shareable URL" claim, not just an assertion that a string was built correctly — **reloading a real, complete share URL in a fresh page load restores the exact original shader source into the editor.** All 9 checks passed on the first real run after the gallery feature was added.

**A real DOM-vs-CodeMirror-model gotcha caught while validating the gallery, not a product bug.** An early version of the gallery check read `document.querySelector(".cm-content")?.textContent` to confirm a gallery click loaded a shader's real multi-line content, and interpreted the result — `"a = sin(uv.x * 10.0 + time)b = sin(uv.y..."`, with no newline between lines — as a bug where line breaks were being lost. They weren't: CodeMirror renders each line as its own block-level `<div class="cm-line">` with no explicit `\n` text node between them, so `textContent` (which flattens all descendant text nodes with no separator) drops the inter-line breaks that were never actually missing from the editor's real document model. Confirmed by checking `.cm-line` element *count* (correctly 6 for a 5-line-plus-trailing-newline shader) and each line's own individual `textContent` instead, and separately by inspecting the generated GLSL panel (which only a correctly-parsed, correctly-newlined multi-statement EZSL program could have produced at all) — both matched the real source exactly. This was a genuine "the test was wrong, not the code" case, caught by cross-checking against a second, independent signal (the compiled GLSL) before concluding anything about the actual gallery-loading logic.

## A real workspace-detection footgun repeated and avoided

Following the exact lesson from `docs/architecture/presets-library.md` (an `npm install` run inside a subdirectory with no `package.json` of its own silently modified the *root* `ezsl` package instead), `ezsl-playground/package.json` was created **before** running `npm install` here — confirmed directly, both immediately after install (root `package.json` has no `dependencies` key) and again after the full verification pass, that the root package was never touched.

## What this doesn't cover

- **No community submission or moderation mechanism.** The gallery is real and built (see "The gallery: curated, not community-submitted" above) — what's missing is the ability for anyone other than a contributor to this repository to add a new gallery entry, which would need a backend to accept and store submissions and ongoing human moderation to review them before they're publicly visible. Neither is in scope for an automated build pass.
- **No deployment to a real hosted URL.** Built and validated locally via Vite's dev server; deploying to GitHub Pages (or any other static host) is part of the broader, not-yet-addressed v1.0.x Deliverables ("Full documentation site live at project domain") and needs the user's own hosting/domain decisions.
- **No EZSL-specific CodeMirror language mode** — `@codemirror/lang-cpp`'s C-family highlighting is a reasonable approximation, not a real EZSL grammar-aware mode (unlike the VS Code extension's real TextMate grammar — see `docs/architecture/vscode-extension.md`). Building a real CodeMirror EZSL mode is a natural, isolated follow-up if this becomes a real usability gap.
- **No mobile/touch-specific UI adjustments** — the three-panel split-view layout is designed for a desktop-width viewport; not tested on or adapted for narrow/touch viewports.
