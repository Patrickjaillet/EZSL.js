# EZSL.js — Multi-Pass & Buffers (v0.5)

Internal design doc for the v0.5.x "Multi-Pass & Buffers (Shadertoy-style)" milestone. Read `docs/architecture/transpiler-pipeline.md` (v0.1 core, especially the runtime — Stage 5) first — this doc covers the new multi-pass orchestration layered on top of the single-pass `mount()` that all prior milestones used.

## Why multiple files, not a JS-side single-file config

`ROADMAP.md`'s v0.5 wording ("Buffer/Pass declaration API... `Image` conceptual model") doesn't specify a syntax. Two shapes were considered: a single `.ezsl` file with `pass BufferA { ... } pass Image { ... }` blocks, or one `.ezsl` file **per pass**, orchestrated by a new JS API. The latter was chosen: every pass is a complete, ordinary `.ezsl` program — same grammar, same `compileEzsl`, no new EZSL syntax at all — and a new JS function, `createPipeline(canvas, { passes: {...} })`, wires multiple compiled passes together. This keeps the language itself unchanged (a single-pass `.ezsl` file compiled by `compileEzsl`/`mount()` today is *already* a valid one-pass "pipeline" — v0.5 doesn't touch that path), matches Shadertoy's own mental model (`BufferA` and `Image` genuinely are separate files/tabs there too), and avoids a second, EZSL-native cross-file-reference mechanism when the JS host language already has one (an object literal of named sources).

## The one new piece of EZSL syntax: `Name.sample(uv)`

Sampling another pass's output is the only thing that needed new EZSL grammar — reading a texture isn't expressible with existing statements/expressions. `MethodCallExpression` (`src/parser/ast.ts`) is a new AST node for `object.method(args)`, added by extending `Parser.parsePostfix` (`src/parser/parser.ts`): after parsing `.identifier`, if a `(` immediately follows, it's a method call instead of a `MemberExpression`. This is deliberately narrow — EZSL has no first-class functions or general method-call semantics; `.sample(...)` is a special form the compiler recognizes, not a general mechanism other builtins could plug into without their own dedicated handling.

### Compile-time buffer-name resolution

`CompileOptions.bufferNames?: string[]` (`src/compiler/compile.ts`) is a new, optional compile option: the set of pass names in the same pipeline this program is allowed to sample from. `compile()` uses it two ways:

1. A **bare identifier** matching a declared buffer name is rejected with a clear error (`'BufferA' is a pipeline buffer, not a value — use 'BufferA.sample(uv)' to read a pixel from it`) rather than silently becoming an implicit `float` uniform the way any other unrecognized identifier would (see `docs/architecture/transpiler-pipeline.md`'s uniform-inference rule) — a bare `BufferA` reference is almost certainly a mistake (forgetting `.sample(uv)`), and the old implicit-uniform fallback would have silently compiled it into nonsense.
2. A **`Name.sample(uv)`** call, where `Name` is a declared buffer, compiles to `texture(u_buffer_Name, uv)` and registers a `sampler2D`-typed uniform (`u_buffer_<Name>`) — reusing the existing `Program.uniforms` mechanism rather than inventing a parallel "buffer inputs" list. `EzslType` (`src/codegen/types.ts`) and `ResolvedType` (`src/compiler/types.ts`) both gained a `sampler2D` variant for this. `.sample(...)`'s receiver must be a bare identifier (not an arbitrary expression) and its one argument must be `vec2`-typed — both checked, both `CompileError` on violation.

### Why dependency discovery reuses `compile()` instead of a separate AST scan

`createPipeline`'s orchestrator (`src/runtime/pipeline.ts`) needs to know, for each pass, which other passes it actually depends on — for both topological ordering and cycle detection. Rather than write a second pass over the AST to find `.sample()` calls (duplicating logic `compile()` already has), `compilePasses` just compiles every pass with **every pipeline pass name** passed as `bufferNames`, then reads off `program.uniforms.filter(u => u.type === "sampler2D").map(u => u.name)` — the compiler has already done the only discovery that matters (which `.sample()` calls survived compilation, after argument-count/type validation), so the orchestrator gets a *validated* dependency list for free instead of a merely-syntactic one a separate scanner would produce (which could include a `.sample()` call that's actually malformed and would never have compiled).

## Dependency ordering and cycle detection

`topologicalOrder` (`src/runtime/pipeline.ts`) is a standard DFS-based topological sort with in-progress-set cycle detection, run once per `createPipeline()` call — **before any WebGL context, framebuffer, or draw call exists**, matching the roadmap's explicit requirement ("compile-time error, not runtime freeze"). A cycle is reported with the actual cycle path (`A -> B -> C -> A`), not just "a cycle exists somewhere."

**A pass that samples itself is not a cycle** — it's a feedback buffer (see below), explicitly excluded from cycle detection (`if (dep === name) continue`). This is the deliberate distinction the whole ping-pong mechanism exists to make correct: a same-frame cycle (`A` needs `B`'s *this-frame* output before `B` has rendered) is genuinely unsatisfiable and rightly an error; a feedback reference (`A` reads `A`'s *last-frame* output) is not a same-frame dependency at all and is exactly what real Shadertoy-style feedback effects need. Tested explicitly in `tests/pipeline.test.ts` (self-reference allowed; 2-pass and 3-pass genuine cycles rejected; a diamond dependency graph and a linear chain both order correctly).

## Ping-pong buffering

`PingPongBuffer` (`src/runtime/pipeline.ts`) holds two `RenderTarget`s (`a`/`b`) and a `frontIsA` flag. Each frame, a feedback pass renders into `.back` (the target not currently exposed for sampling) while any pass sampling it (including itself) reads `.front` (last frame's completed output); `swap()` flips which is which after the frame. A non-feedback buffer just uses one plain `RenderTarget` and never swaps — ping-ponging a buffer nothing reads from itself would be pure overhead. This is the standard technique for feedback effects (trails, fluid sim, cellular automata) — reading and writing the *same* texture in one draw call is undefined behavior in WebGL2, so a feedback buffer structurally cannot use a single render target the way a straight-through buffer can.

## Rendering order and per-pass uniform binding

The runtime frame loop (`createPipeline`'s inner `frame()`) walks `order` (the topologically sorted pass list) once per animation frame, and for each pass: binds that pass's target framebuffer (or `null` — the canvas — for `Image`), sets `u_time`/`u_resolution` and any user-set uniforms (via `setUniform`, same API shape as single-pass `mount()`), binds every buffer this pass depends on to a distinct texture unit (`gl.activeTexture(gl.TEXTURE0 + n)`, incrementing per binding), draws the fullscreen quad, then swaps the pass's ping-pong buffer if it has one. Because `order` is already dependency-sorted, by the time a pass runs, every buffer it might sample has *already rendered this frame* (its `.front`, for a feedback buffer, is last frame's — correct — since the swap for *this* pass hasn't happened yet when a downstream pass reads it).

## Configurable buffer precision and the `EXT_color_buffer_float` trap

`PassSource.format?: "RGBA8" | "RGBA16F" | "RGBA32F"` (default `RGBA8`) lets a buffer pass request higher-precision storage — needed for feedback accumulation that would otherwise band/clip at 8-bit precision. Per the roadmap's own v0.5 trap callout, `RGBA16F`/`RGBA32F` require the `EXT_color_buffer_float` WebGL2 extension, which **is not guaranteed** to be present (common gap on older mobile GPUs). `detectColorBufferFloatSupport` checks `gl.getExtension("EXT_color_buffer_float")` once per `createPipeline()` call; a pass requesting a float format on a device without the extension is silently downgraded to `RGBA8` with a `console.warn` naming the pass — not a thrown error, matching the roadmap's explicit "gracefully degrade... rather than throwing" instruction. This was implemented, but **not verified against a real float-format-unsupported device** — the environment used to validate this milestone (see below) supports the extension, so the degrade path is exercised by code review and the format-selection logic, not by an observed real fallback.

### A real bug caught while implementing this: `texImage2D`'s format/type must agree

The internal format enum (`gl.RGBA16F`, etc.) and the pixel-transfer *type* argument to `gl.texImage2D` are two separate parameters that must be consistent — `RGBA16F`/`RGBA32F` storage requires transferring as `gl.FLOAT`, `RGBA8` requires `gl.UNSIGNED_BYTE`; passing the wrong type for a given internal format is a driver-level error. An early version of `createRenderTarget` computed the transfer type by comparing the *internal format enum value* against `gl.FLOAT` (`gl.FLOAT === internalFormat ? gl.FLOAT : gl.UNSIGNED_BYTE`) — which can never be true, since `internalFormat` is always one of the `RGBA*` enums, never literally `gl.FLOAT`. Every buffer would have received `gl.UNSIGNED_BYTE`, silently breaking `RGBA16F`/`RGBA32F` requests. Fixed by deriving both the internal format *and* the matching transfer type from the same `BufferFormat` string in one place (`glFormatAndType`), rather than trying to reverse-engineer the type from the already-resolved GLenum.

## What v0.5 deliberately doesn't implement

- **Verified `EXT_color_buffer_float`-unsupported fallback behavior** — the degrade-to-`RGBA8` path exists and is code-reviewable, but wasn't observed happening on a real device lacking the extension (none was available in this environment). Worth revisiting if a report of banding/incorrect-looking feedback effects comes in from a real low-end device.
- **Passes sampling each other's non-`Image` outputs across more than a simple DAG shape** — the topological sort handles arbitrary DAGs correctly (tested with a diamond graph), but no example exercises more than a 2-buffer pipeline; deeper graphs are logically covered by the same algorithm but not empirically exercised end-to-end in a browser.
- **Vertex-stage or multi-target (MRT) rendering** — every pass is still a single fullscreen-quad fragment shader with one color output, matching v0.1's runtime model. Vertex-stage EZSL authoring is `v0.6.x` scope (Three.js integration); this milestone didn't touch it.
- **Automatic canvas-resize handling for buffer render targets** — buffer textures are sized once, at `createPipeline()` time, from the canvas's dimensions at that moment; resizing the canvas afterward does not currently resize the underlying buffer framebuffers. A future fix would need to recreate render targets (losing their accumulated contents, which is the correct behavior for a resize) on a resize observer.

## Validated example

`examples/multi-pass/` (two files: `BufferA.ezsl`, `Image.ezsl`) implements a classic feedback-trail effect: `BufferA` samples its own previous frame, fades it (`* 0.92`), and draws a new dot at an animated position on top; `Image` just samples and displays `BufferA`. Confirmed in a real Chromium browser (via Playwright) across two screenshots ~1.5 seconds apart: the trail visibly persists and fades behind a moving bright dot, tracing the expected circular path — proof that the ping-pong swap, inter-pass sampling, and per-frame accumulation are all actually working, not just compiling. Run with `npm run example:multi-pass`. Also exercised (compile + link only, not visually) in the cross-browser integration suite (`docs/architecture/integration-testing.md`) across Chromium/Firefox/WebKit.
