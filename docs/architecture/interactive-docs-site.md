# EZSL.js — Interactive Documentation Site (v1.0.x)

Internal design doc for the v1.0.x Ecosystem Launch "Interactive documentation site" deliverable (live-editable code blocks embedded in every doc page; a progressive tutorial track from beginner through intermediate to advanced/Escape Hatch). Read `docs/architecture/online-playground.md` first — the live-block mechanism here is a deliberately smaller, embeddable version of the same `compileEzsl`/`mount()`/`swapProgram()` real-time loop the Playground uses, applied inside a Markdown-rendered documentation page instead of a dedicated editor UI.

## Scope: both roadmap sub-items, three explicit content-strategy decisions

- **Live-editable code blocks embedded in every doc page** — done, but scoped to EZSL-language code blocks specifically (` ```ezsl ` fences), not every code sample on the site (see "Only EZSL fences are live" below).
- **Progressive tutorial track (beginner → intermediate → advanced/Escape Hatch)** — done, as a 3-tier, 9-page navigation structure.

Three architectural/content decisions were made explicitly via user choice before implementation, rather than assumed:

1. **Content source: reuse and restructure existing docs, not write new content from scratch.** The beginner tier is `docs/ezsl-language-reference.md` split into thematic pages; the intermediate tier reuses the three existing `docs/tutorials/*.md` files directly (see "Intermediate tier: imported, not duplicated" below); the advanced tier is a task-oriented reformulation of `docs/architecture/escape-hatch.md`.
2. **Architecture: a hand-built static site (Vite + build-time Markdown rendering), not a framework.** VitePress and Docusaurus were explicitly considered and rejected, consistent with this project's established pattern of avoiding heavy dependencies where a lighter option suffices (the CLI's hand-written argv parsing, the dev server's zero-dependency `node:http` server, the Playground's CodeMirror-not-Monaco choice — see `docs/architecture/online-playground.md`).
3. **Beginner-tier structure: multiple short thematic pages, not one long reference page.** `docs/ezsl-language-reference.md` was split into 5 pages (`content/beginner/01-hello-gradient.md` through `05-builtins-and-uniforms.md`), each short enough to read in one sitting and each ending in a "What's next" cross-link to the following page.

## Architecture: fully static, zero backend, build-time Markdown

Like the Playground, the entire site — navigation, Markdown rendering, live code blocks, WebGL2 previews — runs client-side with no server component beyond serving static files. Unlike a typical static-site generator, Markdown is **not** pre-rendered to HTML at build time as separate output files; instead, each `.md` file is imported as a raw string via Vite's `?raw` import suffix (`declare module "*.md?raw"` in `src/vite-env.d.ts`, the same pattern `examples/*/main.ts` already established for `.ezsl?raw`) and rendered to HTML **in the browser**, on navigation, via `marked` (`src/markdownRenderer.ts`). This keeps the site a single-page app with hash-based client-side routing (`window.location.hash`, a `hashchange` listener in `src/main.ts`) — no server-side routing, no per-page HTML files to generate, and no build step that needs to know the full page list ahead of a Markdown-parsing pass (`src/pages.ts`'s `PAGES` array is itself the only page manifest, imported directly by `main.ts`).

## Content structure: `src/pages.ts` as the single navigation manifest

`PAGES: Page[]` (`{ slug, title, tier, markdown }`) is the one place page order, titles, and tier grouping are declared. `main.ts`'s `renderNav()` groups pages by `tier` (`"Beginner" | "Intermediate" | "Advanced"`) and renders a heading per tier, in `PAGES` array order — so reordering or retiering a page is a one-line change in `pages.ts`, not a change to any rendering logic.

### Intermediate tier: imported, not duplicated

`three-js-scene.md`, `multi-pass-shadertoy.md`, and `canvas2d-compositing.md` are imported directly from the main repo's `../../docs/tutorials/*.md?raw` — not copied into this package's own `content/` directory. This was a deliberate content-strategy decision, not an oversight: duplicating the files would create two copies that could silently drift apart (the exact failure mode the project has repeatedly avoided elsewhere — `ezsl-presets`' README explicitly cross-references rather than restates package docs, and the multi-pass/Three.js/Canvas2D architecture docs are each referenced from `README.md` rather than re-summarized inline). Because these tutorials already use the same ` ```ezsl `/` ```typescript ` fence-language convention as the beginner-tier content this package authored directly, the shared `renderMarkdown()` pipeline needs no special-casing to make their EZSL fences live — confirmed live in a real browser (see "Validation" below): `three-js-scene.md`, loaded unmodified from its original location, correctly mounts exactly 2 live blocks (its vertex and fragment EZSL sources) and renders its other 5 `typescript`/`bash`-tagged blocks as ordinary static code.

## Only EZSL fences are live

`markdownRenderer.ts`'s `renderMarkdown()` overrides `marked`'s `code()` renderer: a fence tagged ` ```ezsl ` renders as a `<div class="ezsl-live-block" data-source="...">` placeholder (source URI-encoded into the `data-` attribute); every other language tag (` ```typescript `, ` ```bash `, plain untagged fences) renders as an ordinary static `<pre><code>` block. This matches the fence-language convention `docs/tutorials/*.md` already used before this milestone existed (EZSL snippets tagged `ezsl`, orchestration/setup code tagged by its real language) — no content file needed to change its own fence tags to work with this renderer.

**A real API gotcha found while building this:** `marked` v14's renderer-override API has no "call the built-in renderer for everything I'm not overriding" mechanism — overriding `code()` at all means the override is responsible for producing correct output for *every* language, not just the one being special-cased. The non-`ezsl` fallback path in `code()` manually reproduces `marked`'s own default code-block HTML (language-string extraction, trailing-newline normalization, `&`/`<`/`>`/`"` escaping via a small local `escapeHtml()` helper) — read directly from `node_modules/marked/lib/marked.esm.js`'s real `_Renderer.code()` implementation rather than guessed, after an initial draft that assumed a `return false`-style fallback convention didn't exist and every non-EZSL fence rendered as a raw, unescaped, unwrapped string.

After the page's HTML is inserted into `#content`, `liveBlock.ts`'s `mountAllLiveBlocks()` finds every `.ezsl-live-block` placeholder and replaces it with a real `mountLiveBlock()` widget (see below) — a two-phase render (Markdown → placeholder HTML, then placeholder → live widget) rather than mounting CodeMirror/WebGL2 directly inside the `marked` renderer callback, since `marked`'s renderer API only returns HTML strings, not real DOM nodes or side effects.

## `mountLiveBlock`: a smaller, embedded version of the Playground's compile loop

`liveBlock.ts`'s `mountLiveBlock(container, initialSource)` builds, inside the given container: a CodeMirror 6 editor (same `@codemirror/lang-cpp` + `oneDark` choice as the Playground, for the same reasons — see `docs/architecture/online-playground.md`'s "Editor" section) and a small 160×160 WebGL2 preview canvas with an absolutely-positioned error overlay. Its `recompile()` function follows the identical three-step shape the Playground's own `recompile()` and `ezsl dev`'s client script both use (compile → on `LexError`/`ParseError`/`CompileError` show a formatted overlay and stop, leaving the last-good frame showing → on success, `mount()` on first compile or `swapProgram()` on every later one), debounced 150ms per keystroke. `formatEzslError`/`isEzslPipelineError` (`src/formatError.ts`) are a second, independent local copy of the same reimplementation `ezsl-playground/src/formatError.ts` already carries — not a shared import between the two sibling packages, for the same reason given there: `src/cli/formatCliError.ts` is a frozen-API-external internal CLI module, not meant to become new public `ezsl` API just to serve two other packages' formatting needs (see `docs/API_STABILITY.md`).

This widget is deliberately smaller than the Playground's own editor: no GLSL split-view panel, no gallery, no shareable-URL mechanism — just "edit this snippet inline, in place, on the doc page you're reading, and see it recompile and re-render live." A doc page can and does host multiple independent live blocks (e.g. `content/beginner/04-functions-structs-arrays.md` has 3 — one each for functions, structs, and arrays); each gets its own independent `EzslRuntimeHandle` and its own WebGL2 context, since they are genuinely separate programs edited independently, not views onto one shared shader.

## Cross-page linking: hash routes in the rendered site, plain relative paths in the source files

The `.md` source files themselves are written with ordinary, real relative filesystem paths (`./02-values-and-types.md`, `../architecture/three-integration.md`) — deliberately, so they continue to read correctly as plain Markdown outside this site (on GitHub, or when `docs/tutorials/*.md` cross-references `docs/architecture/*.md` from outside this package entirely, which this renderer leaves completely untouched). Inside the rendered site, `markdownRenderer.ts`'s `link()` renderer override rewrites any `href` ending in `.md` (optionally with a trailing `#anchor`) to a working hash route: `rewriteMarkdownLinkToHashRoute()` takes the link's basename, strips the `.md` extension, and strips a leading `\d+-` numeric prefix (matching this package's own `NN-topic-name.md` beginner-content file-naming convention) — so `./02-values-and-types.md` becomes `#/values-and-types`, matching the real page `slug` in `pages.ts`. This function only rewrites; it does not validate that the resulting slug actually exists in `PAGES` (a broken cross-link would render as a dead hash route rather than a build-time error) — an accepted trade-off for a hand-built site with no page-manifest-aware Markdown linting, consistent with the project's general posture of not building tooling infrastructure beyond what a milestone actually needs.

Note that a `.md` reference that appears only as inline code text (single backticks, e.g. `` `docs/architecture/three-integration.md` ``) is not a Markdown link at all and is never passed to `link()` — several `docs/tutorials/*.md` cross-references to architecture docs are written this way intentionally (prose references, not navigable links), and the rendered site correctly leaves them as plain inline code with no hash-route rewriting.

## Validation

Two layers, following the project's established "prove it in a real browser, not just unit tests" standard for anything runtime-facing:

1. **`tests/markdownRenderer.test.ts`** (6 Jest cases) — `rewriteMarkdownLinkToHashRoute`'s pure link-rewriting logic (numeric-prefix stripping, parent-directory basename extraction, anchor stripping, non-`.md` links left untouched). `renderMarkdown()`'s actual `marked` wiring and the `ezsl-live-block` placeholder mechanism are deliberately **not** unit-tested here — what matters is the real rendered DOM and mounted widgets, which the integration suite below covers directly against a real browser, not marked's internal call sequence.
2. **`tests/docsSite.integration.mjs`** (`npm run test:integration`, a real Playwright/Chromium session against a real running Vite dev server, mirroring `ezsl-playground/tests/playground.integration.mjs`'s pattern) — confirms, in a real browser: the default route loads the first beginner page with exactly 1 live block; the 3-tier nav renders all 9 pages in the correct Beginner/Intermediate/Advanced grouping and order; a page with multiple live blocks (`functions-structs-arrays`, 3 blocks) mounts exactly that many, each independently; navigating via hash route updates the active nav-link highlight; editing a live block's source to valid EZSL recompiles without showing the error overlay; the intermediate-tier `three-js-scene` page — loaded directly from `docs/tutorials/`, not duplicated — correctly mounts exactly 2 live blocks (its vertex and fragment EZSL sources) alongside 5 correctly-rendered static (non-live) code blocks; an in-content Markdown link rewrites to a working `#/`-prefixed hash route; the advanced Escape Hatch page loads with its correct title and its 1 live block; and there are zero uncaught page errors across the entire flow. All 13 checks passed on the first full run after two test-script bugs (not product bugs — see below) were fixed.

**Two real test-script bugs caught and fixed while writing the integration suite, not product bugs.** (1) An early assertion compared `.nav-tier-heading` elements' `textContent` against `["BEGINNER", "INTERMEDIATE", "ADVANCED"]` (all-caps) and failed — the actual DOM text is mixed-case (`"Beginner"`, etc.); the visual all-caps rendering comes from CSS (`text-transform: uppercase` in `index.html`'s embedded stylesheet), which `textContent` never reflects. Fixed by asserting the real mixed-case text instead of the visually-rendered transform. (2) An early assertion expected at least one rewritten `#/`-hash link on the `three-js-scene` page and failed — that page's own `.md` references to other docs (e.g. `docs/architecture/three-integration.md`) are written as plain backtick-quoted inline code, not real Markdown link syntax, so `renderMarkdown()` correctly produces no `<a href>` for them at all (see "Cross-page linking" above). Fixed by moving the link-rewrite check to the `hello-gradient` beginner page instead, which does end in a real Markdown "What's next" link. Both were confirmed as test-premise errors, not rendering bugs, before the fix — the same "verify against a second independent signal before concluding" discipline used to resolve the Playground gallery's `textContent`-flattening question (see `docs/architecture/online-playground.md`).

## A real workspace-detection footgun repeated and avoided

Following the same lesson documented in `docs/architecture/presets-library.md` and `docs/architecture/online-playground.md` (an `npm install` run inside a subdirectory with no `package.json` of its own silently modifies the *root* `ezsl` package instead), `ezsl-docs-site/package.json` was created before running `npm install` here, and root `package.json`'s `dependencies` key was confirmed still empty (`0` matches from `grep -c '"dependencies"'`) after every install and again after the full verification pass.

## What this doesn't cover

- **No deployment to a real hosted URL.** Built and validated locally via Vite's dev server, and confirmed to produce a real static production bundle (`npm run build`, deployable to GitHub Pages or any static host — same posture as `ezsl-playground`). Actual deployment needs the user's own hosting/domain decisions, tracked under the broader v1.0.x "Full documentation site live at project domain" deliverable.
- **No search.** Navigation is the 3-tier sidebar only; there is no full-text or fuzzy search across pages.
- **No syntax-highlighting mode specific to EZSL** for the *static* (non-live) code blocks that appear in intermediate/advanced content (e.g. the `typescript` setup snippets in the Three.js tutorial) — these render as plain, unhighlighted `<pre><code>` text. Only live blocks get real CodeMirror syntax highlighting (via `@codemirror/lang-cpp`, the same C-family approximation the Playground uses — see `docs/architecture/online-playground.md`).
- **No broken-link validation.** `rewriteMarkdownLinkToHashRoute()` rewrites unconditionally without checking the resulting slug exists in `pages.ts`'s `PAGES` array (see "Cross-page linking" above) — a typo'd or stale cross-link would silently produce a dead hash route rather than a build-time error.
- **No mobile/touch-specific UI adjustments** — the fixed 240px sidebar + max-width content layout targets a desktop-width viewport, same scope boundary as the Playground.
