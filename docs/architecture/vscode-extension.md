# EZSL.js — VS Code Extension (v0.7, part 4)

Internal design doc for the two "VS Code extension" items of v0.7.x "Developer Experience": syntax highlighting for `.ezsl` files, and inline type hints (hover tooltips showing inferred GLSL type). This is the fourth and final v0.7.x item.

**Scope note**: unlike every prior v0.7.x item, this one lives in its own package (`vscode-extension/`), not `src/`/`dist/` — it's a genuinely separate deliverable (its own `package.json`, its own build, its own runtime environment) that *depends on* the `ezsl` package rather than being part of it.

## Two sub-items, two very different amounts of work

Syntax highlighting is a static TextMate grammar (`syntaxes/ezsl.tmLanguage.json`) — no runtime code, no dependency on the compiler, just a declarative token-matching ruleset VS Code's own tokenizer runs. Hover type hints are fundamentally different: they require running the *actual* EZSL type-inference pass against whatever text is currently open in the editor and reporting a real, compiler-derived answer — not a hand-maintained approximation that could drift from the real compiler's behavior. This asymmetry shaped the whole implementation: the grammar was written directly against the language's real syntax (cross-checked against `docs/architecture/ezsl-grammar.ebnf.md`, the authoritative EBNF), while the hover feature required a small, deliberate addition to the compiler itself (see below) before the extension could be built at all.

## Syntax highlighting: `syntaxes/ezsl.tmLanguage.json`

A standard TextMate grammar, registered for the `ezsl` language id (`language-configuration.json` + the `contributes.grammars` entry in `package.json`) and the `.ezsl` file extension. Highlights: keywords (`if`/`else`/`for`/`in`/`return`), `fn`/`struct` declarations (with the declared name scoped as `entity.name.function`/`entity.name.type`), type-constructor/cast names (`vec2`/`vec3`/`vec4`/`mat2`/`mat3`/`mat4`/`float`/`int`/`bool`/`array`), auto-injected builtins (`uv`/`time`/`resolution` for fragment stage, `position`/`normal`/Three.js camera matrices for vertex stage, `color`/`glPosition` as output names — see `CLAUDE.md`'s boilerplate-injection section and `docs/architecture/three-integration.md`), numeric literals, swizzle/method-call member access (`.xyz`, `.sample(uv)` — v0.5 multi-pass), and the `glsl { ... }` Escape Hatch block, which is highlighted by embedding `source.glsl` (a separate, commonly-installed GLSL grammar extension) when available, falling back to a minimal self-contained pattern set otherwise — the block's contents are opaque to EZSL's own grammar by design (see `docs/architecture/escape-hatch.md`), so there's no way to write EZSL-native rules for what's inside it.

## Hover type hints: what had to change in the compiler first

Before this milestone, `compile()` had no way to report "what type did variable X end up as" after the fact — its internal `TypeScope` (a name→type map, `src/compiler/typeInference.ts`) is a closure-local implementation detail, built up and then discarded once `compile()` returns a `Program`. A hover provider needs exactly that map (or something equivalent) to answer "what's the type at this cursor position," and no public API produced it.

**The chosen approach** (explicit user decision): rather than exposing `TypeScope` itself, or refactoring `compile()`'s return shape, a new optional `CompileOptions.onVariableDeclared?(name, type, pos)` callback was added — called once for every new local variable declaration the compiler encounters, in source order, with its inferred type as a display string (`glslTypeName`, e.g. `"float"`, `"vec3"`) and its `.ezsl` position. This is deliberately a debug/tooling *hook*, not a new field on `Program`: it changes nothing about `compile()`'s return value or behavior when omitted (verified directly — `tests/onVariableDeclared.test.ts`'s "does not affect the compiled Program's shape or content when provided" case compiles the same source with and without the hook and asserts identical output), and it's wired in at exactly the two places `compile.ts` already declares a new local — `emitAssignmentInScope` (a first assignment to a name) and the `ForStatement` handler (a loop counter, always typed `int`). Function parameters and uniforms are **not** covered (uniforms already have a complete answer via `Program.uniforms`; function parameters are out of scope for this milestone — see "What this doesn't cover" below).

`collectVariableDeclarations(source, options?)` (`src/compiler/index.ts`, exported from the package root) wraps the whole `tokenize → parse → compile` pipeline with this hook already wired in, returning a flat list of `{ name, type, line, column }`. Unlike `compileEzsl`, it **does not throw** on a `LexError`/`ParseError`/`CompileError` — it returns whatever declarations were collected before the failure. This is the one deliberate behavioral difference from every other public compile entry point in the library, and it's deliberate for exactly one reason: the intended caller is a hover provider running continuously against a document that is, most of the time, in some mid-edit, temporarily-invalid state — a hover feature that goes blank on every syntax error while typing would be far less useful than one that keeps showing whatever it last successfully inferred. A genuine non-pipeline error (a real bug, not a user source mistake) is still rethrown, not swallowed.

## Extension architecture: single package, in-process hover provider (explicit user decision)

Two architectures were considered: a full Language Server Protocol (LSP) server (reusable by any LSP-compatible editor — Neovim, Sublime, etc.) with a thin VS Code client, versus a single extension registering a hover provider directly against the VS Code API in the Extension Host process. **The single-extension approach was chosen** — the roadmap item explicitly asks for a VS Code extension, not a general editor-agnostic tool; a full LSP server is meaningfully more code (a JSON-RPC transport, a server lifecycle, document-sync handling) for a feature this milestone only needs to prove once. `src/extension.ts` registers a `vscode.languages.registerHoverProvider("ezsl", { provideHover })` — on every hover, it finds the word under the cursor, calls `collectVariableDeclarations` against the *entire current document text*, and returns the matching declaration's type as a Markdown code block (`vscode.MarkdownString` + `appendCodeblock`). Matching is by **name**, not by exact declaration position — hovering any occurrence of a variable (not just its first assignment) reports its type, which is both simpler and more useful than requiring the cursor to land exactly on the declaring line.

## ESM-from-CJS, and a real bundling bug found while building this

`ezsl` is a pure ESM package (`"type": "module"`); VS Code extensions conventionally ship as CommonJS (`main` in `package.json` pointing at a `require()`-able file). `require("ezsl")` cannot load an ESM package — only a dynamic `import()` can, and `import("ezsl")` is what `src/extension.ts` uses.

Because the extension has no `node_modules`-based dependency resolution at runtime (see next section for why), the actual shipped artifact is a single bundled `dist/extension.js`, produced by `esbuild.config.mjs` (`bundle: true`, `external: ["vscode"]`, everything else — including all of `ezsl`'s compiled output — inlined). **A real bug was found and fixed while building this**: an earlier version wrapped the `import()` call in `new Function("specifier", "return import(specifier)")`, specifically to dodge a *different*, real problem — TypeScript's `tsc`, when compiling to a CommonJS module target, downlevels a literal `import()` expression into a `require()` call, which would have defeated the entire point (since `require()` cannot load ESM). That workaround did solve the `tsc`-only case, but it silently broke the *bundled* case: esbuild's bundler only resolves and inlines `import()` calls it can see statically in the source — hiding the call behind `new Function(...)`'s opaque string argument made it invisible to esbuild's dependency graph too, so the "bundled" output still contained a real runtime `import("ezsl")` that happened to keep working only because `node_modules/ezsl` (a `file:..` symlink to the entire monorepo root) was still present locally — not something a packaged, distributed `.vsix` could rely on. Confirmed directly: inspecting the bundle's line count (79 lines — clearly not containing the ~700-line compiler) and grepping for `require("ezsl")`/`import("ezsl")` in the output showed the dependency was never actually inlined. Switching to a plain, literal `await import("ezsl")` — with `tsc` used only for `typecheck` (which doesn't care about downleveling, only type correctness) and esbuild doing the *actual* build/emit — fixed both problems at once: esbuild statically resolves and inlines the literal `import()` at build time, so the shipped bundle (2586 lines afterward, correctly containing `CompileError`/`TypeScope`/`glslTypeName` and every other compiler symbol the hover path touches) never performs any module resolution against `ezsl` at runtime at all.

## Why bundling was necessary at all (not just an optimization)

`ezsl` is installed in the extension's `node_modules` as `file:..` — npm's local-path dependency mechanism, which here resolves to a symlink pointing at the **entire monorepo root** (`src/`, `tests/`, `examples/`, `docs/`, everything — there's no separate "publishable subset" directory). Packaging the extension with `node_modules/ezsl` included as-is (the default behavior without an explicit ignore) would have shipped the whole repository inside the `.vsix`, which is both wrong in size and exposes far more than a hover provider needs. `.vscodeignore` excludes `node_modules/**` entirely, and `esbuild.config.mjs`'s bundle step is what makes that safe — the compiled `dist/extension.js` needs nothing from `node_modules` at runtime, `ezsl`'s relevant code is already inlined into it.

## Real, live validation (not just unit tests)

Following this project's standing rule for runtime-facing features, this was validated by actually launching a real VS Code Extension Development Host (`code --extensionDevelopmentPath=vscode-extension/ demo/shader.ezsl`) — not just by reading the bundled output or trusting the unit tests below — and confirming, via screenshots:

- **Syntax highlighting**: a real `.ezsl` file (`vscode-extension/demo/shader.ezsl`) opened with correct, distinct coloring for function calls (`length`, `vec3`), numeric literals, identifiers, and swizzle/member access, and the status bar's language-mode indicator correctly reading "EZSL."
- **Hover, scalar type**: hovering the identifier `d` (declared via `d = length(uv - 0.5)`) showed a tooltip reading exactly `float d`.
- **Hover, vector type**: hovering `trail` (declared via `trail = vec3(d, d, d)`) showed `vec3 trail`.
- Re-validated after the esbuild-bundling fix above, against the newly-bundled `dist/extension.js`, to confirm the fix didn't just make the bundle self-contained on disk but that the *running* extension still behaved identically.

## What this doesn't cover

- **Hover for uniforms.** `Program.uniforms` already has a complete, correct answer for these (no compiler change needed), but this milestone's hover provider only consults `collectVariableDeclarations`'s locals list — a real, scoped gap, not an oversight; extending hover to uniforms is a small, natural follow-up that wasn't required to satisfy this milestone's roadmap wording.
- **Hover for function parameters** (`fn`-declared, always inferred `float` per `docs/architecture/type-system.md`'s asymmetry note) or struct field types.
- **Diagnostics/red squiggles** for compile errors — the roadmap's two sub-items are highlighting and hover only; a `vscode.languages.registerDiagnosticCollection` integration (using the same `collectVariableDeclarations`-style partial-result approach) would be a natural, separate follow-up.
- **Auto-completion.**
- **Publishing to the VS Code Marketplace.** The extension is built and validated locally; no `vsce publish` was run, and no publisher identity beyond the placeholder `"publisher": "ezsl"` in `package.json` is configured.
- **Editors other than VS Code.** See "single package, in-process hover provider" above for why an LSP server (which would generalize to other editors) wasn't built.

## Tests

Core-library tests (in the main package, not the extension):
- `tests/onVariableDeclared.test.ts` (9 cases) — the `CompileOptions.onVariableDeclared` hook itself: fires once per distinct local in source order, not on re-assignment, correct types for scalar/vector locals and `for`-loop counters, correct position, not called for uniforms, and — critically — doesn't alter `compile()`'s output when provided.
- `tests/collectVariableDeclarations.test.ts` (7 cases) — the convenience wrapper: full declaration lists, partial results before a `CompileError`/`ParseError`/`LexError` rather than throwing, passthrough of a caller-supplied `onVariableDeclared` alongside its own collection, and passthrough of other `CompileOptions` (e.g. `bufferNames`).

The extension itself has no separate Jest suite — its logic is a thin call into already-tested core-library functions (`collectVariableDeclarations`) plus VS Code API glue with no independent business logic to unit-test; it was instead validated via the real Extension Development Host screenshots described above, consistent with how this project validates every other runtime-facing feature (real browsers for the WebGL2 runtime, a real dev-server session for `ezsl dev`, a real Chromium tab for DevTools source maps) rather than only unit-testing the parts that can be unit-tested.
