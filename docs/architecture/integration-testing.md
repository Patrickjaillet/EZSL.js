# EZSL.js — Cross-Browser Integration Testing

Internal note on two roadmap deliverables served by the same suite: the "Alpha" phase deliverable (`ROADMAP.md`, end of v0.2.x–v0.4.x, *"Integration test suite: transpile + compile on Chrome, Firefox, Safari WebGL2 contexts"*) and the v1.0.x Quality & Coverage deliverable (*"Cross-browser compatibility matrix validated (Chrome, Firefox, Safari, Edge — desktop + mobile)"*). One script, `tests/integration/run.mjs`, is the source of truth for both — extended with a fourth engine (real Microsoft Edge) when the v1.0.x item was addressed, rather than duplicated into a second suite.

## What exists

`tests/integration/run.mjs` (`npm run test:integration`): starts a Vite dev server for `examples/_harness/` (a page that `import.meta.glob`s every `examples/<name>/shader.ezsl`, compiles each through `compileEzsl` — with the same `customFunctions`/etc. options each example's own `main.ts` uses, mirrored in the harness — and calls `mount()` on a throwaway canvas), then drives that page in **four separate real browser engines/products** via Playwright: Chromium, Firefox, WebKit, and (real, locally-installed) Microsoft Edge. For each, every example's actual `WebGLProgram` link result is checked (not just "did `compileEzsl` not throw" — a full round-trip through the real GLSL codegen and a real `gl.linkProgram` call, per engine). `examples/error-demo` is special-cased as *expected* to fail at link (it deliberately demonstrates a v0.4 translated compile error — see `docs/architecture/error-translation.md`); every other example is expected to link successfully.

This is a genuine engine-level check, not a mock: Firefox's and WebKit's GLSL ES front-ends are different codebases from Chromium's ANGLE, so this catches anything EZSL's codegen emits that happens to be tolerated by one driver's parser but not another's — a real risk for a transpiler whose only prior validation (`docs/architecture/transpiler-pipeline.md`, `docs/architecture/type-system.md`) was exclusively against Chromium.

## What "Chrome, Firefox, Safari, Edge" means here, honestly

- **Chrome / Chromium**: real, automated, via Playwright's bundled Chromium.
- **Firefox**: real, automated, via Playwright's bundled Firefox.
- **Edge**: real — `chromium.launch({ channel: "msedge" })` drives the actual, separately-installed Microsoft Edge binary on the machine running the suite (Playwright's own documented "browser channels" mechanism, not a Chromium instance relabeled). Edge and Chromium share ANGLE as their GLSL-to-native translation layer, so a genuine engine-level difference showing up here specifically (as opposed to Firefox/WebKit) is less likely in practice, but the check is real, not assumed. **Not Playwright-managed** — unlike Chromium/Firefox/WebKit (always available after `npx playwright install`), Edge must already be installed on the host machine; its absence is treated as a graceful `SKIPPED`, not a suite failure, since not every machine (e.g. a Linux CI runner) will have it.
- **Safari**: **there is no real Safari involved.** This environment is Windows; Safari doesn't run on Windows at all, and there's no macOS available to test against real Safari/WebKit. "WebKit" in this suite is Playwright's bundled WebKit build — the same open-source engine Safari is built on, but not Safari itself, and not necessarily the same version or platform-specific configuration real Safari ships. It's the closest available proxy, not a substitute claim of "tested on Safari." If real Safari coverage becomes a requirement, it needs either a macOS CI runner or manual testing on an actual Mac — nothing in this repository can provide that today.
- **"Desktop + mobile"**: **desktop only.** Playwright's mobile "device" presets (`Pixel 5`, `iPhone 13`, etc.) emulate a mobile *viewport and user-agent string* inside the same desktop browser engine binary — they do not exercise a genuinely different mobile GPU driver, a different ANGLE backend, or real mobile OS/browser behavior (Chrome for Android, real mobile Safari on iOS). Running this suite through those device presets would produce green output that doesn't actually validate anything a real mobile device's shader compiler could disagree on — worse than not claiming mobile coverage at all, since it would look like real coverage without being any. Real mobile validation would need either a device farm (e.g. BrowserStack, Sauce Labs) or physical devices, neither available in this environment; this is stated as an open gap, not silently treated as covered.

The v1.0.x roadmap item is therefore **partially met, explicitly**: Chrome, Firefox, and Edge coverage is real, automated, and engine-genuine; Safari coverage is WebKit-proxy only; mobile coverage does not exist. This mirrors how the original Alpha-deliverable version of this same doc treated the "Safari" gap — called out directly rather than glossed over.

## Result (most recent run)

All 29 example "units" in `examples/` (single-pass shaders plus `multi-pass`/`three-integration`/`canvas2d-interop`) compiled through the full EZSL pipeline and linked successfully as real `WebGLProgram`s in Chromium, Firefox, WebKit, and Edge alike (`examples/error-demo` correctly failed to link in all four, as designed). No engine-specific GLSL acceptance differences were found in this pass — everything EZSL currently generates happens to be portable across all four engines' GLSL ES 3.00 front-ends. This is a snapshot, not a guarantee: it should be re-run whenever the codegen (`src/codegen/glslGenerator.ts`) or the compiler's GLSL-emitting logic (`src/compiler/compile.ts`) changes in a way that could plausibly affect what GLSL text gets produced.

## Running it

```bash
npm run build     # tests/integration/run.mjs imports from dist/, not src/ — via examples' own src/ relative imports actually, see note below
npm run test:integration
```

Note: `examples/_harness/main.ts` (like every other example's `main.ts`) imports directly from `../../src/index.js` (compiled TypeScript resolved by Vite at dev-server time, not from `dist/`) — so `npm run build` isn't strictly required before `test:integration`, but keeping it in the habitual sequence matches every other example's dev workflow and catches a `src/` compile error before spending time spinning up multiple browser engines.

Firefox and WebKit must be installed once via `npx playwright install firefox webkit` (Chromium is typically already present from earlier Playwright use in this project's development — see `docs/architecture/transpiler-pipeline.md`'s validated-examples methodology, which established the Playwright-for-real-browser-validation pattern this suite formalizes). This is a manual one-time local setup step, not automated by `npm install` — Playwright's browser binaries are large (Firefox alone is ~120MB) and deliberately not bundled into every `npm install`. Edge is not installed by Playwright at all — it must already be present on the host as a regular application install; the suite detects and gracefully skips it if it isn't.
