# EZSL.js — API-Diff CI Check (v1.0.x)

Internal design doc for the v1.0.x "Semantic versioning enforcement via automated API-diff CI check" deliverable. Read `docs/API_STABILITY.md` first — that document defines *what* counts as a breaking change and *why*; this doc covers the mechanism that actually checks for one.

## What this catches, and why "the tests pass" isn't enough

Jest's test suite (443 tests as of this writing) validates *behavior* — that `compileEzsl` produces correct GLSL for known inputs, that `mount()` renders correctly, and so on. It does **not** validate that the *public API's shape* hasn't silently changed — a parameter added to `mount()`'s signature, a field removed from `MountOptions`, an export deleted from `src/index.ts` — none of that fails an existing test unless a test happens to exercise exactly the changed surface, which is exactly the failure mode a real API break slips through: the internal call sites all get updated to match, every existing test still passes with the new shape, and a consumer's code (never in this repository, so no test here could ever catch it) breaks on upgrade. This check exists specifically to catch *that*, independent of whether behavior is otherwise correct.

## How it works: three pieces

1. **`scripts/extractApiSurface.mjs`** — loads `src/index.ts` through the real TypeScript Compiler API (not a textual scan, and not `dist/index.d.ts`'s own re-export statements, which never show a re-exported type's actual resolved shape — see below) and produces `{ exportName: "resolved type text" }` for every name `src/index.ts` exports. A function's entry is its full callable signature (parameters, defaults, return type); an `interface`'s entry is every member's name, optionality, and resolved type, expanded and alphabetically sorted (so a reordering of an interface's own field declarations — which changes nothing about its actual shape — never produces a spurious diff).
2. **`scripts/api-surface-baseline.json`** — a committed snapshot of that surface, captured at the last deliberate version boundary via `node scripts/checkApiDiff.mjs --write-baseline` (which also records the `package.json` version it was taken at, in the sibling `api-surface-baseline.version.txt`).
3. **`scripts/checkApiDiff.mjs`** (wired as `npm run check-api-diff`) — re-extracts the current surface, diffs it against the baseline, and:
   - Reports newly **added** exports as informational only (adding an export is never breaking).
   - Reports **removed** or **changed-shape** exports as breaking.
   - If any breaking change is found, checks whether `package.json`'s major version component is greater than the baseline's — if so, the breaking change is treated as an accepted, deliberate part of that major release (exit 0, informational); if not, it fails (exit 1) with the specific diff, since a breaking change without a corresponding major bump violates the SemVer commitment `docs/API_STABILITY.md` describes.

## Why the TypeScript Compiler API, not a text diff of `.d.ts` files

`dist/index.d.ts` (the file `tsc -p tsconfig.json` actually emits for the package root) is just a sequence of `export { X } from "./mod.js"` re-export statements — TypeScript doesn't inline a re-exported type's shape into the re-exporting module's own `.d.ts`. A raw text diff of `dist/index.d.ts` across two versions would therefore only ever detect a name being added or removed from that re-export list — it would never notice that `MountOptions` itself gained or lost a field in `dist/runtime/bootstrap.d.ts`, which is exactly the kind of change this check most needs to catch. Loading the whole program through `ts.createProgram` and asking the real `TypeChecker` to resolve each exported symbol's *aliased* declaration (via `checker.getAliasedSymbol`, since a `export type { X } from "./mod.js"` symbol is itself just an alias with no local declaration to inspect) gives the actual, fully-resolved shape regardless of which file it's declared in.

## A real resolution bug found while building this

An early version of `extractApiSurface.mjs` called `checker.getDeclaredTypeOfSymbol(symbol)` directly on each exported symbol and printed `"any"` for every single `interface`/`type` export (`GeneratedFragmentShader`, `MountOptions`, `Program`, all of them) — only function exports resolved correctly. The cause: a symbol coming from a bare re-export (`export type { X } from "./mod.js"`) is an **alias** symbol with no declarations of its own; `getDeclaredTypeOfSymbol` on an aliased symbol with nothing to declare against silently falls back to `any` rather than erroring, which made the bug easy to miss at a glance (the script ran, produced JSON, just wrong JSON) rather than crashing loudly. Fixed by resolving through `checker.getAliasedSymbol(symbol)` first to reach the real originating symbol (in its actual declaring module) before asking for its declared type. A second, related gap: even after that fix, an `interface`'s own declared type printed as just its bare name (e.g. `"MountOptions": "MountOptions"`) rather than its member shape — `typeToString` doesn't expand interface members by default, only type-alias bodies (`ts.TypeFormatFlags.InTypeAlias` only helps the latter). Fixed by explicitly walking `checker.getPropertiesOfType(type)` and rendering each member's own resolved type text for any interface-flagged export, rather than relying on `typeToString` to do it. Both bugs were caught by eyeballing the very first real run's output against what the actual exported interfaces look like in source — not by a test asserting the *tool's* own correctness (there isn't one; see "What this doesn't cover" below).

## The WGSL/WebGPU exemption

`generateWgslFragmentShader`, `layoutUniformBuffer`, `wgslAlignmentFor`, and their associated types are listed in `checkApiDiff.mjs`'s `EXPERIMENTAL_EXEMPT` set — changes to these are never flagged as breaking, regardless of version, matching `docs/API_STABILITY.md`'s explicit carve-out for the still-experimental WGSL target (never validated against a real `GPUDevice` — see `docs/architecture/webgpu-target.md`). This is a small, explicit, visible list in the script itself, not inferred from a naming convention (e.g. "anything with `Wgsl` in the name") — a reviewer reading `checkApiDiff.mjs` can see exactly what's exempted and cross-reference it against the stability doc's own reasoning, rather than trusting an implicit pattern match to stay correct as new exports are added.

## Regenerating the baseline

`node scripts/checkApiDiff.mjs --write-baseline` overwrites `scripts/api-surface-baseline.json` and `scripts/api-surface-baseline.version.txt` with the current surface and the current `package.json` version. This is a **deliberate, reviewed action** taken at a real version boundary (after intentionally shipping a breaking change in a major release, or simply to establish the very first baseline, as done here at `v0.1.0` ahead of the v1.0.0 freeze) — never something to run reflexively just to make a failing check pass. A failing `check-api-diff` run is telling you one of two true things: either the change needs a major version bump it doesn't have yet, or the change wasn't supposed to be breaking in the first place and the actual code should be revisited — `--write-baseline` doesn't resolve which of those is true, a human does.

## What this doesn't cover

- **No automated test suite for `extractApiSurface.mjs`/`checkApiDiff.mjs` themselves.** They were validated by hand: running the extractor against the real `src/index.ts` and eyeballing the output (catching the two resolution bugs above), then deliberately introducing a real removal and a real shape change into a working copy of `src/index.ts`/`src/codegen/glslGenerator.ts`, confirming the check correctly flagged both (exit 1, correct diff text) before reverting. This mirrors the project's validation posture for other one-off tooling scripts, but is a real gap relative to the rest of the codebase's test coverage.
- **Not wired into an actual CI pipeline** (e.g. a GitHub Actions workflow) — there is no CI configuration in this repository yet. `npm run check-api-diff` is available to run manually (or from whatever CI system is eventually configured) but nothing currently runs it automatically on push/PR.
- **No detection of behavioral-only breaking changes** — a function whose signature is textually identical but whose runtime behavior for previously-valid inputs changed (see `docs/API_STABILITY.md`'s "bug-fix exception" for how those are judged) is invisible to a pure type-shape diff. This check is a safety net for *shape* regressions specifically, not a substitute for the judgment `docs/API_STABILITY.md` describes for behavioral ones.
