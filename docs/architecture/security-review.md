# EZSL.js — Security Review (v1.0.x)

Internal record of the v1.0.x Quality & Coverage "Security review of Escape Hatch injection paths (no arbitrary JS execution surface via shader strings)" deliverable. Performed manually (the project's `/security-review` skill requires a git repository, which this project does not currently have — see below) by tracing every place user-supplied or otherwise externally-influenced string data flows through the codebase, looking specifically for a path into `eval`, `new Function`, `child_process`, or unguarded filesystem access.

## Why this wasn't run via the `/security-review` skill

The project's `/security-review` skill requires an initialized git repository to operate against (it diffs against a git history). This repository does not currently have a `.git/` directory — a deliberate, explicit choice made earlier in this same v1.0.x work session (the user chose to defer git/GitHub synchronization, newly requested in `ROADMAP.md`'s own conventions, and continue with the in-progress API-stability work instead). This review was therefore performed directly: manual code tracing, live exploitation attempts against a running instance, and direct fixes — not automated diff-based analysis. If/when this repository is initialized as a git repo, a follow-up `/security-review` pass would be a reasonable complement to this one, particularly for any code written after this review.

## Finding 1 (the roadmap's named concern): Escape Hatch — no JS execution surface, confirmed structurally

**The roadmap's literal question — can `glsl { ... }`/`defineFunction` shader text reach JavaScript execution — has a structural "no," not just a "no bugs found today."** Traced the complete data flow: a `glsl { ... }` block's captured text (`RawGlslStatement.source`, `src/parser/ast.ts`) and a `defineFunction`-registered `glslSource` string both flow, unmodified as plain text, into `Program.body`/`Program.topLevel` (`src/codegen/types.ts`), which `generateFragmentShaderMapped` (`src/codegen/glslGenerator.ts`) concatenates into a single GLSL source **string**. That string's only consumer, anywhere in the codebase, is `gl.shaderSource()` + `gl.compileShader()` (`src/runtime/bootstrap.ts`) — real WebGL API calls that hand the string to the browser's native GPU driver for compilation as GLSL, never back into a JavaScript evaluation context of any kind. Confirmed by grepping the entire `src/` tree for `eval(`, `new Function(`, `child_process`, `exec(`/`execSync`/`spawn(` — the only real hit is `src/errors/throwAtEzslLine.ts`'s indirect `eval`, a wholly separate mechanism (see Finding 2) with no connection to shader text at all. There is no code path, buggy or otherwise, by which a `.ezsl` author's `glsl { ... }` block or a host application's `defineFunction` call could reach JavaScript execution — the architecture itself rules it out, independent of any input validation.

**A worst-case Escape Hatch payload is a GLSL compile/link failure, nothing more.** Maliciously crafted raw GLSL inside a `glsl { ... }` block can, at most, produce an intentionally-broken shader (a compile error, translated per `docs/architecture/error-translation.md`) or — in principle, since the block is genuinely unvalidated GLSL — GPU-side resource exhaustion (an extremely expensive shader that hangs the GPU/browser tab), which is a real but qualitatively different risk class than code execution, and one inherent to *any* system that lets a user author and run arbitrary GLSL (Shadertoy, GLSL sandboxes generally) — not something specific to or newly introduced by EZSL's Escape Hatch design.

## Finding 2: `ezsl dev`'s static-file route — real, exploitable path traversal (found and fixed)

**Confirmed live, not theoretical.** `src/cli/devServer.ts`'s catch-all static route (serving `dist/` for the client script's `import { mount } from "/index.js"` to resolve) passed the raw incoming `req.url` into `path.join(DIST_ROOT, url)` with a code comment explicitly (and incorrectly) claiming this was safe: *"No path-traversal guard beyond Node's own URL parsing is added here: this server is a local development tool bound to localhost."* Neither half of that claim held up under direct testing:

- `path.join` does **not** sandbox `..` segments — confirmed directly: `join(DIST_ROOT, "/../package.json")` resolved to a real file one directory above `DIST_ROOT`.
- A live `ezsl dev` session, hit with a real `node:http` client request (`GET /../package.json`), returned **HTTP 200 with the full contents of the project's own `package.json`** — a file outside the intended `dist/` serving root.

**Compounded by a second real bug.** `server.listen(port, callback)` — with no host argument — binds to `::` (all network interfaces) by Node's own documented default, not `127.0.0.1`/localhost-only as the same comment claimed. Confirmed via `server.address()` before the fix (`{"address":"::", ...}`) and via `netstat` after the fix (`127.0.0.1:<port> LISTENING`, confirming the corrected binding). Combined, these two findings meant: **anyone who could reach a developer's machine on the local network — not just the developer themselves — could read arbitrary files from that machine's filesystem** (bounded by relative path depth and OS file permissions) for as long as `ezsl dev` was running, with no authentication of any kind. This is a meaningfully worse severity than either bug alone.

### The fix

- **`resolveWithinRoot(root, url)`** (`src/cli/devServer.ts`) — a new helper that resolves the requested URL against the serving root via `path.resolve` and explicitly verifies the result is still inside that root (comparing against `root + path.sep` as a prefix, not a naive string-contains check, which would itself be bypassable by a sibling directory sharing a name prefix) before any filesystem access is attempted; returns `null` (treated as a 404 by the caller) for anything that would escape. Handles both raw (`/../package.json`) and percent-encoded (`/..%2fpackage.json`) traversal attempts (URL-decoded before the containment check, with a safe fallback to the raw string if decoding fails on malformed input, rather than throwing).
- **`server.listen(port, "127.0.0.1", res)`** — the host argument is now explicit, making the server genuinely loopback-only, matching what the removed comment had incorrectly claimed all along.

Both fixes were verified live, against a real running `ezsl dev` instance, before and after: the exact `GET /../package.json` request that previously returned 200 with real file contents now returns 404, a URL-encoded variant of the same attack also returns 404, legitimate requests (`/index.js`, `/shader.ezsl`, nested `dist/` paths) continue to work exactly as before, and `netstat` confirms the server now binds to `127.0.0.1` specifically rather than all interfaces. 4 new regression tests (`tests/devServer.test.ts`) pin both fixes into the ordinary `npm test` suite: two for the traversal guard (raw and encoded), one confirming legitimate nested paths still resolve, one confirming the `"127.0.0.1"` argument is present at the exact call site (a source-text assertion, deliberately chosen over a black-box network probe for a negative — proving a port is *not* reachable from a non-loopback interface isn't reliably testable inside a sandboxed Jest environment that may itself have no such interface) plus a real, live `fetch` confirming the server still answers correctly on loopback with the fix in place.

## Finding 3: `defineFunction`'s trust boundary is a host-application concern, correctly scoped

`defineFunction(name, glslSource, signature)` (`src/compiler/index.ts`) accepts a raw GLSL string and a caller-declared signature, both trusted at face value — `docs/architecture/escape-hatch.md` already documents this precisely ("the `glslSource` is trusted to actually implement what `signature` claims"). This is architecturally correct, not a gap: `defineFunction` is a **JavaScript-side, host-application-level API call** (invoked from a `main.ts`/application code, not from `.ezsl` shader source an untrusted third party could author), analogous to any API that takes a string of code/config from its own caller — the trust boundary is "does the *host application developer* trust their own call site," not "does EZSL protect against a malicious `.ezsl` file." A `.ezsl` file itself has no way to invoke `defineFunction` or influence its arguments — that capability exists only in TypeScript/JavaScript calling code. No finding here; confirmed the existing design/documentation already reflects the correct threat model.

## Finding 4: `ezsl build`'s file-writing is a local CLI operator's own filesystem, not a network trust boundary

`runBuild` (`src/cli/commands.ts`) reads a `.ezsl` file at a caller-supplied path and writes a sibling `.glsl` file, both derived from a CLI argument the *local user invoking the CLI* provides on their own command line. This is the same trust model as any CLI tool that takes a file path (e.g. `tsc somefile.ts`, `cp a b`) — the "attacker" would have to already be the person running the command, at which point they already have equivalent-or-greater filesystem access directly. Not a finding; noted to make explicit that this was checked and deliberately not treated the same as `ezsl dev`'s network-facing case (Finding 2), where the trust boundary genuinely is crossed (a remote request handler, not a local command invocation).

## Methodology

- **Static tracing**: grepped the full `src/` tree for `eval(`, `new Function(`, `child_process`, `exec(`/`execSync`/`spawn(`, and for every `readFile`/`writeFile`/`join(` call site that combines a fixed root with externally-influenced input, to build a complete map of where untrusted-adjacent data reaches a sensitive operation.
- **Live exploitation, not just code reading**: for the one finding that looked real (Finding 2), actually started a real `ezsl dev` instance, sent real HTTP requests (via `node:http`'s client, not `fetch`, since `fetch` normalizes `../` out of a URL client-side before a request is even sent — a real attacker using `curl` or a raw socket would not do this normalization, so testing through `fetch` alone would have missed the bug entirely) with real traversal payloads, and confirmed both the vulnerability and, afterward, the fix, by reading real response bodies/status codes and real `netstat` output — not by reasoning about what *should* happen.
- **Escaping-logic stress test**: directly attempted a template-literal-breakout payload against `throwAtEzslLine`'s existing message-escaping (Finding 1's neighbor, `src/errors/throwAtEzslLine.ts` — not shader-string-related, but the codebase's only real `eval` call site, so scrutinized regardless) and confirmed it's neutralized; separately confirmed that even its **unescaped** `ezslUrl` parameter cannot achieve code execution, because the generated eval'd script's structure places `ezslUrl`'s content strictly *after* an unconditional `throw` statement, which JavaScript semantics guarantee aborts the script before any later text is ever reached as code — verified this reasoning directly with a crafted newline-injection payload rather than trusting the structural argument alone.

## What this review does not cover

- **No automated/tool-assisted static analysis** (no CodeQL, Semgrep, or similar was run) — this was a manual, targeted review scoped to the roadmap's specific concern (Escape Hatch → JS execution) plus whatever else surfaced while tracing that concern's neighbors, not an exhaustive audit of the entire codebase's attack surface.
- **No review of third-party dependencies' own security posture** (`three`, `vite`, `playwright`, `typescript`, `jest`, etc.) — out of scope; this review covers code in `src`/`scripts`/`vscode-extension`/`tests` written for this project.
- **The `/security-review` skill itself was not run** — see "Why this wasn't run via the skill" above; a git-repo-based automated pass remains a reasonable follow-up once this repository is under version control.
- **No penetration testing of the (not-yet-existing) hosted playground/docs site** — those are `ROADMAP.md` v1.0.x Ecosystem Launch items, not yet built as of this review.
