# EZSL.js — Canvas2D Interop (v0.6, part 2)

Internal design doc for the "Canvas2D fallback/interop module" part of v0.6.x "Framework Integrations". Read `docs/architecture/transpiler-pipeline.md` (v0.1 core, especially the runtime — Stage 5) first — this doc covers what's new: an alternative output path for an already-compiled fragment program, not a new compilation stage.

**Scope note**: this doc covers Canvas2D interop only. The Three.js bridge is `docs/architecture/three-integration.md`; the WebGPU target (the third v0.6 item) is separate and not covered here.

## What "fallback" actually means here (a roadmap wording clarification)

`ROADMAP.md`'s item is titled *"Canvas2D fallback/interop module: pipe EZSL fragment output into a 2D canvas via texture readback (for environments without WebGL2)"*. Taken completely literally, "for environments without WebGL2" is impossible: an EZSL fragment program is GLSL ES 3.00 running on a real GPU shader pipeline — there is no way to execute it at all without a real WebGL2 context, offscreen or not. **This module does not make EZSL shaders run without WebGL2.** What it actually provides — and what "texture readback" in the roadmap's own wording points at — is: render the shader in a real (offscreen, invisible) WebGL2 context exactly as `mount()` already does, then copy the rendered pixels into a visible `<canvas>` 2D context via `gl.readPixels` + `CanvasRenderingContext2D.putImageData`, rather than displaying the WebGL canvas directly. `mountToCanvas2D`'s own doc comment (`src/runtime/bootstrap.ts`) states this explicitly, specifically so a future reader doesn't go looking for a "no-WebGL2" code path that was never meant to exist.

**The real use case** is compositing: putting EZSL shader output on the *same* 2D canvas as ordinary Canvas2D drawing (`fillText`, `drawImage`, arbitrary shapes) — something `mount()`'s direct-to-WebGL-canvas rendering structurally cannot do, since a WebGL canvas and a 2D canvas are different context types on different `<canvas>` elements. A secondary use case is exporting a single rendered frame as a static image (`once: true`).

## Shared rendering core: `setupWebglRenderer`

Before this milestone, `mount()` (`src/runtime/bootstrap.ts`) compiled/linked the program, set up the fullscreen quad, and ran its `requestAnimationFrame` loop all inline in one function. Adding a second entry point that needed the *same* compile/link/quad/uniform-binding logic but a *different* per-frame action (copy to 2D canvas, not just leave pixels on the WebGL canvas) meant that logic had to be factored out first — `setupWebglRenderer(gl, program, options)` now does the shared work (shader compilation with v0.4 error translation, fullscreen quad setup, uniform location lookup) and returns a `drawFrame(width, height)` function plus `setUniform`. Both `mount()` and `mountToCanvas2D()` call this; `mount()`'s `frame()` loop just calls `drawFrame` and lets the browser display the WebGL canvas directly, while `mountToCanvas2D()`'s loop calls `drawFrame` and then reads the result back. This refactor was deliberately minimal — the actual per-frame GL calls (`gl.viewport`, `gl.useProgram`, uniform binding, `gl.drawArrays`) are untouched, just relocated, so `mount()`'s existing behavior (and its existing browser-validated examples) couldn't regress from this change; confirmed by re-running the full cross-browser integration suite (`docs/architecture/integration-testing.md`) after the refactor, not just by inspection.

## `mountToCanvas2D(canvas2d, program, options)`

1. Acquires a `2d` context on the caller's visible `canvas2d` (thrown if unavailable — a plain DOM/canvas failure, unrelated to WebGL2).
2. Creates its own **offscreen** `<canvas>` element (never appended to the DOM) sized to match `canvas2d`, and acquires a `webgl2` context on *that* — with `preserveDrawingBuffer: true`, required so `gl.readPixels` can read back a frame's contents after the frame has already been submitted (without it, the drawing buffer's contents are implementation-defined the moment control returns to JS).
3. Runs `setupWebglRenderer` against the offscreen context — same compile/link/error-translation path as `mount()`.
4. Each frame: `drawFrame`, then `gl.readPixels` into a reusable `Uint8Array`, then a manual row-by-row copy into a `CanvasRenderingContext2D.createImageData` buffer, then `putImageData`, then the caller's `onFrame` callback (if given) — the intended place to layer Canvas2D drawing on top, using the *same* `ctx2d`, in the same synchronous tick before the browser paints.

### The row-flip bug (found by comparing against `mount()`'s output, not by reading a GL spec)

`gl.readPixels` reads rows starting from GL's origin, which is the **bottom-left** of the framebuffer (the same bottom-left-origin convention `docs/architecture/transpiler-pipeline.md` already documents for `gl_FragCoord`, and the reason EZSL's own `uv` builtin is Y-flipped for authors). `ImageData`, on the other hand, is row-ordered top-to-bottom, matching ordinary 2D canvas/DOM convention. Copying `readPixels`' output directly into an `ImageData` buffer without accounting for this renders the frame **vertically flipped** relative to what `mount()` would show for the identical program on a plain WebGL canvas — a real bug, not a hypothetical one, caught while building this feature by rendering `examples/canvas2d-interop/`'s shader through both `mount()` and `mountToCanvas2D()` side-by-side and noticing the vertical mismatch. Fixed by copying row `height - 1 - y` of the `readPixels` buffer into row `y` of the `ImageData` buffer — an explicit per-row reversal, not a single bulk copy.

## `fps` vs. `once`

`gl.readPixels` is a synchronous GPU→CPU transfer — meaningfully more expensive than an ordinary `gl.drawArrays` call that just leaves pixels in the framebuffer for the compositor to display directly, since it forces the GPU pipeline to finish and blocks until the data is available in CPU memory. Running that every `requestAnimationFrame` tick (60fps) for a purely cosmetic composited overlay is often wasteful, so `MountToCanvas2DOptions.fps` (default `30`) throttles the readback loop via `setInterval` instead of chaining `requestAnimationFrame` calls unconditionally; passing `fps: Infinity` opts back into an uncapped `requestAnimationFrame` loop for callers who do need it. `once: true` renders and reads back exactly one frame (ignoring `fps`) for the static-snapshot/export use case — no loop at all.

## What this milestone deliberately doesn't implement

- **Any code path that runs an EZSL shader without a real WebGL2 context.** See "What 'fallback' actually means" above — this was never possible and the module doesn't claim otherwise.
- **Alpha-aware/transparent compositing tricks beyond what `RGBA`+`putImageData` naturally provides.** The shader's alpha channel is read back and copied as-is; if a caller wants the shader to appear transparent over other page content, that's ordinary `color`/alpha authoring in the `.ezsl` source itself (assign a `vec4` with alpha < 1.0 to `color`), not a special feature of this module.
- **Automatic canvas-resize handling.** Like `createPipeline`'s buffer render targets (see `docs/architecture/multi-pass.md`), the offscreen canvas and `Uint8Array` pixel buffer are sized once, at `mountToCanvas2D()` call time, from `canvas2d`'s dimensions at that moment — resizing `canvas2d` afterward does not resize the offscreen renderer or reallocate the pixel buffer.

## Validated example

`examples/canvas2d-interop/` renders a simple animated gradient shader via `mountToCanvas2D` (`fps: 24`) and draws stroked/filled text ("EZSL + Canvas2D") on top via `onFrame`, using the same `CanvasRenderingContext2D`. Confirmed in a real Chromium browser (via Playwright), across two screenshots ~1.5 seconds apart: the gradient is correctly oriented (not vertically flipped — direct confirmation the row-flip fix works, not just a code-reading claim), visibly animates between the two captures (`sin(time)`-driven color shift), and the composited text remains crisp and correctly positioned in both — proof the shader-then-overlay ordering happens every single frame, not just once at setup. Also exercised (compile + a single real `readPixels`/`putImageData`/`onFrame` cycle, not just visually) in the cross-browser integration suite (`docs/architecture/integration-testing.md`) across Chromium/Firefox/WebKit. Run with `npm run example:canvas2d-interop`.
