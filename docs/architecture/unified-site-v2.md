# EZSL.js — Unified Documentation Site v2 (Professional Redesign + Playground Merge)

Internal design doc for the v2 redesign of the live documentation site (`https://patrickjaillet.github.io/EZSL.js/`), a follow-up milestone requested after the v1.0.x "Interactive documentation site" and "Online Playground" deliverables (see `docs/architecture/interactive-docs-site.md` and `docs/architecture/online-playground.md`, both now partially superseded). Three concrete asks drove this: a genuinely professional visual redesign, a Shadertoy-style shader editor merged into the site (not a separate undeployed package), and new EZSL vs GLSL vs Shadertoy vs WGSL comparative learning content, backed by a much larger validated example gallery.

## Why merge, not add a second app

Before this milestone, the repo had two independent implementations of a CodeMirror+WebGL2 EZSL editor: `ezsl-docs-site` (the actually-deployed site, with inline live-code-blocks in markdown) and `ezsl-playground` (a standalone 3-panel Shadertoy-style editor with a 21-shader gallery and shareable URLs) — but `ezsl-playground` had no `vite.config.ts` and no CI/deploy workflow of its own. It was never live. Rather than deploy it separately or build a second, competing editor page, the standalone package was merged wholesale into `ezsl-docs-site` as a new `#/playground` route, then deleted. This eliminated a real, pre-existing duplication (near-identical `recompile()` logic, near-identical `formatError.ts`) rather than adding a third copy.

## Design system: from zero tokens to a real one

The v1 site had a single embedded `<style>` block in `index.html` with every color hardcoded as a literal hex value — no reuse, no consistency mechanism. v2 introduces `src/styles/tokens.css` (CSS custom properties: a neutral gray-scale, a teal accent replacing the previous saturated green, a spacing scale, typography tokens for Inter + JetBrains Mono) plus `layout.css`/`components.css`/`content.css`, each consuming the tokens rather than hardcoding values. This is a mechanical but real change: every color, spacing value, and radius in the site now traces back to one token file.

A genuinely new addition, not present in either predecessor: **mobile responsiveness**. Both `docs/architecture/interactive-docs-site.md` and `docs/architecture/online-playground.md` explicitly listed "no mobile/touch adaptation" as an accepted gap. v2 adds a real `@media (max-width: 900px)` breakpoint with a hamburger-toggled slide-in sidebar and a click-outside-to-close scrim.

**A real bug found while building the mobile nav, not a cosmetic one.** The scrim (`#nav-scrim`, meant to close the sidebar when clicked) was initially given `inset: var(--topbar-height) 0 0 0` — spanning the full viewport width, including underneath the sidebar itself. Since the sidebar (`#nav`) had a higher `z-index` (60 vs. the scrim's 55) and sat at the same `left: 0`, the sidebar's own nav links intercepted the click before it ever reached the scrim in that region — Playwright's `page.click('#nav-scrim')` timed out for real, retrying against an element whose geometric center was covered by an unrelated `<a class="nav-link">`. Caught by the real-browser Playwright suite, not by inspection: the fix was correcting the scrim's bounds to start at `left: var(--sidebar-width)` instead of `left: 0`, so it only covers the area actually outside the sidebar.

## The shared recompile engine: `src/compiler.ts`

Before this milestone, `liveBlock.ts`'s inline-snippet widget and the (now-merged) Playground's full editor page each hand-implemented the identical "compile → format-error-on-failure → mount-or-swapProgram, 150ms debounce" state machine — confirmed near-line-for-line identical by direct comparison, not assumed. `createRecompiler(target: RecompileTarget)` extracts this once; both `liveBlock.ts` and the new `playgroundPage.ts` now call it, with an optional `onGlslOutput` callback that only the full Playground page (which has a GLSL split-view panel) actually uses. No behavior change for existing live blocks — confirmed by the full existing Playwright suite passing unmodified after the refactor.

## Playground routing: `#/playground/<base64>`, not a second parsing scheme

The docs site's router already owns the `#/<slug>` hash namespace (`main.ts`'s `currentSlug()` strips a leading `#/` and treats everything after it as the slug). The standalone Playground's original shareable-URL scheme (`#shader=<base64>`) would have collided with this. Rather than invent a second, independent hash-parsing convention layered on top, the Playground's shader payload became a path segment *after* the route itself: `#/playground/<base64>`. `main.ts`'s router recognizes any slug that is `"playground"` or starts with `"playground/"`, and the rest of the slug (if any) is the base64 payload — one regex, one branch, no second parser. `src/urlState.ts` (ported from the standalone package) was updated accordingly; the actual encode/decode logic (`btoa`/`atob` via a `encodeURIComponent`/`decodeURIComponent` round-trip, to work around `btoa`'s Latin1-only limitation) is unchanged from the original.

## The Comparisons tier and the `.tabs` component

A new 4th nav tier, `"Comparisons"`, sits between Intermediate and Advanced — 5 new pages: an overview clarifying that GLSL/Shadertoy/WGSL are not three peers (Shadertoy specifically is a *convention* on top of GLSL, not a separate language — a real, common point of confusion worth heading off explicitly), a syntax side-by-side page, and three comparison pages (type systems, uniforms/varyings, multi-pass) each reusing/adapting facts already documented elsewhere (`docs/architecture/webgpu-target.md`'s WGSL alignment story, `docs/tutorials/multi-pass-shadertoy.md`'s EZSL-multi-pass-mirrors-Shadertoy framing) rather than re-deriving them.

The syntax-side-by-side page needed an interactive tabbed view switching between 4 code samples — a genuinely new UI pattern not present in either predecessor site. **A real mechanism gotcha found while building this**: markdown supports raw HTML passthrough, so the `.tabs`/`.tabs-nav`/`.tabs-panel` markup is hand-authored directly inside `content/comparisons/02-syntax-side-by-side.md` — but a `<script>` tag embedded in that same raw HTML never executes, because `innerHTML` (which is how `renderPage()` inserts the rendered markdown into `#content`) never runs injected `<script>` elements, by design, in every browser. The first draft of this page included an inline `<script>` for the tab-click wiring and it silently did nothing. Fixed by moving the click-handling logic into a real TypeScript module (`src/tabs.ts`, `mountAllTabs(root)`) called from `main.ts` after every page render — the same "mount after render" pattern `mountAllLiveBlocks()` already used for live code blocks, applied to a second kind of post-render DOM wiring.

## Every WGSL mention carries the same caveat, verbatim

Every comparison page/column touching WGSL gets a `.badge-experimental` pill plus one identical sentence about the validation gap (never compiled against a real `GPUDevice`, unit-tested on generated-text structure only). This is deliberately duplicated prose, not a shared component — a trust-relevant caveat is safer kept literally identical everywhere than refactored into something a future edit could accidentally weaken in one place and not another. The wording mirrors `docs/architecture/webgpu-target.md`'s own established framing rather than inventing new language.

## Gallery expansion: 21 to 33, with a real type-inference trap hit repeatedly

12 new example shaders were authored to fill genuinely missing effect categories the original 21 didn't cover: cellular/Worley noise (`voronoi`), domain warping (`domain-warp`), polar-coordinate repetition (`polar-repeat`), a multi-primitive SDF showcase (`sdf-showcase`), smooth-min metaball blending (`sdf-smooth-union`), hand-written HSV conversion (`hsv-color-cycle`), retro pixelation (`pixelation`), RGB-channel-offset chromatic aberration (`chromatic-aberration`), an analog clock face (`clock`), circular-wave interference (`interference-waves`), randomized quarter-circle tiling (`truchet-tiles`), and distance-based neon glow lines (`glow-lines`). Each lives in its own `examples/<name>/` directory at the repo root, following the exact existing convention — `examples/_harness/main.ts`'s `import.meta.glob("../*/shader.ezsl", ...)` auto-discovers them with zero harness changes needed, confirmed by reading (not assuming) the glob's actual scope.

**A real, repeated compiler-behavior trap found while authoring these — the same one CLAUDE.md already documents for a different case (`length(vec3)` misinference), but a distinct manifestation.** EZSL function parameters are always inferred `float` (documented, deliberate — there's no parameter type annotation syntax). Several of the new shaders' first drafts declared helper functions like `fn sdCircle(p, r) { return length(p) - r }` and called them with a real `vec2` argument (`sdCircle(cell, 0.35)`) — this compiles successfully at the EZSL level (the compiler never rejects the mismatch, since `length(p)` alone doesn't force `p`'s inferred type past `float`), but produces invalid GLSL: the generated `float sdCircle(float p, float r)` is then called with a `vec2` argument, which the real WebGL2 driver correctly rejects (`'dot' : no matching overloaded function found` / `no matching overloaded function found` for the vector-typed calls specifically). This is a real, silent gap between EZSL-level compilation success and GLSL-level correctness for this specific shape of function-parameter usage — not previously hit by any of the original 28 examples, none of which pass a full vector into a helper function this way. It surfaced not from local `compileEzsl()` testing (which passed, since EZSL-side compilation never fails here) but from the project's own cross-browser Playwright suite (`npm run test:integration`), which drives a real WebGL2 driver — exactly the validation layer this gap depends on to be caught at all. 8 of the 12 new examples hit this in some form; all were fixed by restructuring the affected helper functions to take individual scalar components (`fn sdCircle(px, py, r)`) instead of a single vector parameter, with call sites passing `.x`/`.y` explicitly. This gap in EZSL's own compile-time checking (function-parameter argument-type mismatches aren't validated) is a known, pre-existing item — CLAUDE.md's type-system section already lists "argument *type* mismatches" among what's "not checked yet" for `fn`/`defineFunction`/struct constructors; this milestone is a concrete, repeated real-world instance of exactly that gap, not a new discovery, but the first time it was actually hit and had to be worked around rather than just documented as theoretical.

The gallery's `GalleryEntry` type gained an optional `category` field (`"Patterns" | "Noise & Procedural" | "Raymarching" | "Color & Animation" | "SDF Techniques"`) and the Playground's gallery panel now renders category subheadings — a flat 33-item list would have been meaningfully worse UX than the already-borderline flat 21-item list.

## What this doesn't cover

- **No search** — inherited gap from the original site, not addressed here.
- **No broken-link validation** — `rewriteMarkdownLinkToHashRoute()` still rewrites unconditionally without checking the resulting slug exists in `PAGES`.
- **No syntax highlighting for static (non-`ezsl`) code blocks** — same CodeMirror-only-for-live-blocks scope as before.
- **The Comparisons tier's GLSL/Shadertoy/WGSL code samples are illustrative, hand-written text, not independently compiled/validated against a real GLSL/WGSL compiler** — only the EZSL tab's content is a real, live, compiling code block (via the existing live-block mechanism); the other three tabs are static reference text. This matters specifically for the WGSL tab, which carries the same never-run-against-a-real-`GPUDevice` caveat as the rest of the project's WGSL story.
