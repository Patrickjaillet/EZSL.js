# EZSL.js — Preset/Shader Library (`ezsl-presets`) (v1.0.x)

Internal design doc for the v1.0.x Ecosystem Launch "Preset/Shader library (`ezsl-presets` package)" deliverable — the first of the three Ecosystem Launch items to be built. Read `docs/architecture/escape-hatch.md` first (the `defineFunction`/`CustomFunction` mechanism every preset is built on) before making changes here.

## The core design question: how does a preset actually reach a user's shader?

EZSL has no native `import` syntax — a `.ezsl` file cannot pull in another `.ezsl` file's code, and the only mechanism for injecting reusable GLSL into a compiled program is the JavaScript-side `defineFunction(name, glslSource, signature)` API (v0.2 Escape Hatch — see `docs/architecture/escape-hatch.md`), passed via `compileEzsl(source, { customFunctions: [...] })`. This was an explicit, deliberate decision (not a workaround): **every preset in `ezsl-presets` is a pre-built `CustomFunction` value**, exported as a plain ES module export, consumed exactly the way any hand-written `defineFunction` call already is. This directly satisfies the roadmap's own "tree-shakeable individual preset imports" sub-item for free — a `CustomFunction` is just a `{ name, glslSource, signature }` object with no side effects at module-load time, so a bundler can eliminate an unused preset export without any special-casing, and each preset category also has its own `package.json` `exports` subpath (`ezsl-presets/noise`, `/sdf`, `/colorGrading`, `/blurBloom`) so a consumer who wants only one category never even resolves the others' source.

The alternative considered and rejected: shipping presets as raw `.ezsl` source snippets meant to be copy-pasted into a user's own file. This was rejected specifically because it isn't "importable" or "tree-shakeable" in any real JS-tooling sense — it's a documentation pattern, not a package a bundler can reason about, and it doesn't match what the roadmap's own wording ("Tree-shakeable individual preset imports") asks for.

## Where the actual GLSL came from

Every preset's GLSL formula is lifted, verbatim or near-verbatim, from a real, already-validated `examples/` shader in the main `ezsl` repository — not independently invented for this package:

- **`hash2D`/`fbm2D`** (noise) — the exact hash function and 4-octave accumulation loop `examples/fbm-clouds/shader.ezsl` runs inline, factored into reusable GLSL functions.
- **`sdfSphere`/`sdfBox`** (SDF) — the exact distance formulas `examples/raymarch/shader.ezsl` and `examples/raymarch-box/shader.ezsl` compute inline (`length(p - center) - radius`, and the box's outside/inside-distance combination). The 2D variants (`sdfCircle2D`/`sdfBox2D`) are the direct 2D analogues of the same formulas, not independently sourced.
- **`cosinePalette`** (color grading) — the identical cosine-palette formula already registered under the name `hueShift` in `examples/escape-hatch/shader.ezsl`.
- **`luminance`/`saturate`/`contrast`** (color grading) — standard, well-known formulas (Rec. 709 luminance weighting; saturation via lerp toward grayscale; contrast via an S-curve around mid-gray) with no example-shader precursor, since no existing example happened to need color grading specifically — the one category built without a direct in-repo source to copy from.
- **`boxBlur9`/`gaussianBlur13`/`brightnessThreshold`** (blur/bloom) — standard, well-known real-time-rendering techniques (a 3×3 box-filter average; a 13-tap bilinear-optimized Gaussian approximation; luminance thresholding as bloom's usual first stage), same situation — no existing `examples/` shader happened to need texture blurring, since blur/bloom is inherently a multi-pass-only concept (see below) and none of the existing multi-pass examples (`examples/multi-pass/`) implement blur.

This traceability was a deliberate choice while writing each preset's own doc comment (in `src/noise.ts`/`sdf.ts`/`colorGrading.ts`/`blurBloom.ts`) — a reader should be able to see, for the majority of presets, exactly which already-cross-browser-validated example the formula is drawn from, rather than trusting a freshly-written formula on faith.

## Namespace collisions: each preset that needs a helper renames it internally

`compile()`'s existing collision rules (see `docs/architecture/escape-hatch.md`) reject two `customFunctions` registered under the same name. `fbm2D` internally needs the same hash function `hash2D` also exports — if both were registered together under the identical GLSL function name `hash2D`, that would be a real, silent risk (whichever one a bundler happened to keep, or an outright compile error if both survived tree-shaking) the moment a consumer imported both from the noise module. The fix: `fbm2D`'s own `glslSource` declares its hash helper under a **different**, collision-avoiding GLSL name (`hash2D_fbm2D`, not `hash2D`) — so importing `hash2D` and `fbm2D` together registers two distinct GLSL functions with no name clash, confirmed directly by a real compile-through-`compileEzsl` test (`tests/presets.test.ts`'s "can both be registered together without a name collision" cases). The same pattern is used for `saturate`'s internal luminance calculation (`luminance_saturate`, distinct from the standalone `luminance` preset's own `luminance` name) — every preset with an internal helper follows this convention, checked by a dedicated "registered together" test per category.

## Blur/bloom's real constraint: `sampler2D` presets can't be called via ordinary EZSL syntax

A blur/bloom preset needs a texture to blur — but the *only* way a `sampler2D` value exists in an EZSL program at all is as the auto-bound buffer-sampling uniform inside a v0.5 multi-pass pipeline (`createPipeline`, `<PassName>.sample(uv)` — see `docs/architecture/multi-pass.md`), and EZSL's `.sample(uv)` syntax has no way to pass "which buffer" as an ordinary function argument to another function (a buffer name is explicitly not a plain value in EZSL's grammar — see `docs/EZSL_LANGUAGE_SPECIFICATION_v1.0.md` §12). Concretely, there is no EZSL-syntax way to write `boxBlur9(BufferA, uv, texelSize)` — `BufferA` isn't callable/passable as a value.

The resolution: these presets are designed to be called from inside a `glsl { ... }` Escape Hatch block, where the raw GLSL identifier the compiler already generates for a `.sample()`-eligible buffer name (`u_buffer_<BufferName>`, a real, plain `sampler2D` GLSL uniform under the hood — see `docs/architecture/multi-pass.md`) is directly nameable and passable to any function, since a `glsl { ... }` block's contents are opaque, unvalidated GLSL text, not constrained by EZSL's own grammar at all. This is documented explicitly in `blurBloom.ts`'s own module doc comment and demonstrated as a real, compiling worked example in both the README and `tests/presets.test.ts` (a 2-pass pipeline shape, `BufferA` + `Image`, with `Image.ezsl` calling `boxBlur9(u_buffer_BufferA, uv, 1.0 / resolution)` from inside a `glsl {}` block) — not asserted to work, actually compiled and verified via `compileEzsl` with `bufferNames: ["BufferA"]` set, matching exactly what `createPipeline`'s own internal orchestration passes.

## Validation

Two layers, matching the project's established "don't just assert it compiles, actually run it" standard for anything runtime-facing:

1. **`tests/presets.test.ts`** (17 cases) — every preset compiled through a real `compileEzsl(source, { customFunctions: [preset] })` call with real EZSL source calling it by name, asserting the generated GLSL's shape (the function signature appears correctly in `topLevel`) for the value-returning presets, and a real multi-pass-shaped compile (via `bufferNames`) for the `sampler2D`-taking blur/bloom presets. Every category that has an internal-helper-naming risk (noise, color grading) has a dedicated "registered together, no collision" test.
2. **`demo/`** (a small Vite page, `npx vite ezsl-presets/demo`) — three presets (`fbm2D`, `sdfSphere` via a hand-written raymarch loop calling it, `cosinePalette`) actually `mount()`ed onto real WebGL2 canvases and confirmed, via a real Chromium browser session (Playwright), to render correctly: visible noise texture for `fbm2D`, a correctly shaded raymarched sphere for `sdfSphere`, a smooth rainbow gradient for `cosinePalette` — not just "the compile call didn't throw."

## Package structure

Mirrors `vscode-extension/`'s established pattern for a separate-but-monorepo-adjacent package: its own `package.json`/`tsconfig.json`/`jest.config.js`, `ezsl` as both a `peerDependency` (what a real consumer needs) and a `devDependency` (`file:..`, for local building/testing against this repo's own `ezsl` source). **A real npm-workspace-detection footgun was hit and fixed while setting this up**: running `npm install ezsl@file:.. --save` from inside `ezsl-presets/` *before* that directory had its own `package.json` caused npm to walk up and silently modify the **root** `ezsl` package's `package.json`/`package-lock.json` instead (adding a nonsensical `"ezsl": "file:"` self-dependency and creating a self-referencing `node_modules/ezsl` symlink pointing at the project's own root) — confirmed by inspecting the root `package.json` immediately after and finding the unexpected entry. Fixed by reverting the root package files and re-running the install only after `ezsl-presets/package.json` existed, which correctly scoped the install to the new package instead. The lesson generalizes: **always create a subdirectory's own `package.json` before running `npm install` inside it** — an `npm install` with no local `package.json` to anchor to will walk up the directory tree looking for one, which in a monorepo-adjacent layout like this project's (`vscode-extension/`, `ezsl-presets/`, both siblings of the root `ezsl` package) means it can silently land on the wrong `package.json` instead of failing loudly.

## What this doesn't cover

- **No `ezsl-presets` npm publish** — built and validated locally; publishing to the real npm registry is part of the broader, not-yet-addressed v1.0.x "Deliverables" section (`v1.0.0 published to npm`), which needs the user's own npm account/credentials.
- **A relatively small preset set** — one or two presets per roadmap-named category (noise, SDF, color grading, blur/bloom), not an exhaustive effects library. Chosen to demonstrate the package's mechanism and validation approach solidly rather than spread thin across many under-tested effects; growing the set is a natural, low-risk follow-up (each new preset just needs the same "real compile + collision check" test pattern already established).
- **No true two-pass separable Gaussian blur** — `gaussianBlur13` is a well-known single-pass bilinear-optimized approximation, not a mathematically exact separable Gaussian (which would need two passes, horizontal then vertical) — a reasonable practical tradeoff for a preset library, not a numerically rigorous implementation.
