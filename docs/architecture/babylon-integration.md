# EZSL.js — Babylon.js Integration (v2.0 direction)

Internal design doc for the Babylon.js game-engine bridge — modeled closely on the existing, working Three.js integration (`src/integrations/three.ts`, `docs/architecture/three-integration.md`). Read that doc first; this one focuses on what's genuinely different for Babylon.js, not on re-explaining the shared design (two-files-not-new-syntax vertex/fragment authoring, `time`/`resolution` auto-registration, etc.).

## Why this needed its own vertex builtin scope, not a reuse of Three's

Babylon.js's real attribute/uniform names, confirmed against `@babylonjs/core@9.23.0`'s actual source (not assumed): `position`/`normal`/`uv` are Babylon's own per-vertex mesh attributes, and `world`/`worldView`/`worldViewProjection`/`view`/`projection`/`viewProjection`/`cameraPosition` are its own auto-bound uniforms. This is a genuine API-shape difference from Three.js, not just a renaming exercise:

- Babylon supplies a combined `worldViewProjection` matrix directly — a vertex shader writes `worldViewProjection * vec4(position, 1.0)`, no separate multiply. Three.js has no equivalent single matrix; its integration always does `projectionMatrix * modelViewMatrix * vec4(position, 1.0)` in-shader.
- Babylon's vertex scope includes real per-vertex UV data (`uv`) — a deliberate, documented name collision with fragment-stage `uv` (which is `gl_FragCoord`-derived). Three's vertex scope has no `uv` at all.
- **No `normalMatrix`-equivalent exists on Babylon's `ShaderMaterial`** — confirmed absent by reading its real auto-bind logic directly (the complete list of uniform names it checks before binding is `world`/`worldView`/`worldViewProjection`/`view`/`projection`/`viewProjection`/`viewProjectionR`/`cameraPosition` — nothing else). `BABYLON_VERTEX_BUILTIN_SCOPE` (`src/compiler/typeInference.ts`) deliberately has no `normalMatrix` entry as a result — a verified omission, not an oversight or an unconfirmed gap.

## The `vertexTarget` mechanism

`src/compiler/typeInference.ts` gained a closed union, `VertexTarget = "three" | "babylon"`, threaded through `TypeScope`/`builtinScopeFor`, `CompileOptions.vertexTarget` (`src/compiler/compile.ts`), and `compileEzslVertex`'s new third parameter, `target` (`src/compiler/index.ts`) — defaulting to `"three"` everywhere, so every pre-existing call site (including every `compileEzslVertex(source)` call in the codebase before this milestone) is unaffected.

A fully generic, caller-supplied scope object (`vertexBuiltinScopes: Record<string, EzslType>`) was considered and rejected. It would let a caller typo a builtin name silently — no fixed name set exists to check a typo against, so `didYouMean` (the compiler's existing Levenshtein-based suggestion mechanism for unknown functions/struct fields) couldn't offer a correction. A closed union keeps type inference and codegen in sync from one named source per target instead.

## The `#version`-never rule — harder than Three's opt-out flag

Confirmed against Babylon's real source (`packages/dev/core/src/Engines/Processors/shaderProcessor.ts`, `Engines/WebGL/webGL2ShaderProcessors.ts`, `Engines/thinEngine.functions.ts`): Babylon's shader processor unconditionally strips any `#version 3` line found in input source, and the real WebGL2 engine always prepends its own `#version 300 es\n#define WEBGL2 \n` at actual compile time — there is no flag or option to suppress or override this. This is a strictly harder constraint than Three's: Three.js supplies its own `#version` line only when explicitly asked to (`glslVersion: THREE.GLSL3`), and EZSL's generator opts out via `includeVersionDirective: false` for that case. For Babylon, there is no scenario where emitting the line is ever correct, so `generateBabylonVertexShaderMapped` (`src/codegen/glslGenerator.ts`) has **no `includeVersionDirective` parameter at all** — not even one defaulted to `false`. This asymmetry with `generateThreeVertexShaderMapped` is documented directly in the function's own doc comment, specifically so a future reader doesn't mistake the omission for an oversight.

## The attribute/uniform auto-generation problem

Babylon's `ShaderMaterial` constructor requires `attributes`/`uniforms` name arrays up front (`options.attributes`, `options.uniforms`) — confirmed, from real source, that anything referenced in the compiled GLSL but missing from these arrays is **silently never bound** (no attribute data, no uniform value written — not a compile error). This is a real, structurally different failure mode from Three.js's "just reference it in source" model, and one this project's "errors that teach" design pillar should not allow to happen silently for anything EZSL itself controls.

A caller-supplied `attributes`/`uniforms` list (mirroring how Three's `materialOptions` merges into the constructor call) was considered and rejected for the same reason as the generic vertex-scope alternative above: it reintroduces exactly the silent-failure risk this integration exists to avoid. Instead, `createBabylonMaterial` (`src/integrations/babylon.ts`) computes both arrays itself, by regex-scanning the compiled GLSL text for Babylon's known builtin attribute/uniform names (`referencedBuiltinNames`, a helper extracted from — and shared with — `generateThreeVertexShaderMapped`'s pre-existing inline logic for Three's 4 matrices) — provably complete for whatever the program actually references, not a guess. `generateBabylonVertexShaderMapped` returns `{ source, sourceMap, referencedAttributes, referencedUniforms }` rather than making the integration module re-derive this by re-scanning the same text a second time, independently — avoiding exactly the kind of "trust one source of truth that turns out incomplete" pattern that caused the real `u_time`/`u_resolution` registration bug in the Three.js integration (ported here as a defensive fix from the start, see below, rather than being rediscovered).

`CreateBabylonMaterialOptions.materialOptions` merges **before** this module's own computed `attributes`/`uniforms` — the opposite order from Three's `materialOptions` (which also can't override `vertexShader`/`fragmentShader`/`uniforms`, but for a coincidentally different reason: those are simply always-required fields there). Here it's deliberate: this integration's own regex-scan-derived lists always win, so a caller can't accidentally reintroduce the silent-failure mode by passing an incomplete list.

## Real bugs found while building this — confirmed in a real browser, not caught by unit tests alone

Two genuine, distinct compile/render failures were found and fixed during real-browser validation (`examples/babylon-integration/`, Playwright/Chromium) — both are exactly the kind of thing this project's validation discipline exists to catch before they ship.

### 1. A real ANGLE compile error: `layout(location = 0)` collision

The first real-browser run failed outright with:
```
FRAGMENT SHADER ERROR: 0:9: 'fragColor' : when EXT_blend_func_extended extension is not enabled, must explicitly specify all locations when using multiple fragment outputs
```
on a shader that only declares *one* fragment output (`out vec4 fragColor;`, no `layout` qualifier) — `generateFragmentShaderMapped`'s standard output, reused as-is for the fragment stage since the Babylon-specific problem turned out to be entirely on the vertex/attribute side, not the fragment codegen itself.

Root cause, confirmed by reading Babylon's real source directly (`WebGL2ShaderProcessor.postProcessor`, `packages/dev/core/src/Engines/WebGL/webGL2ShaderProcessors.ts`): Babylon's fragment post-processor checks the input source for the literal pattern `layout(location = 0) out` via a plain regex — completely independent of whether the shader references `gl_FragColor` or any other specific name. `out vec4 fragColor;` has no such qualifier, so the check fails, and Babylon **injects its own second declaration**, `layout(location = 0) out vec4 glFragColor;`, directly before `void main(`. ANGLE then sees two fragment outputs, neither with dual-source blending support, and rejects the shader — correctly, per the GLSL ES 3.00 spec, since exactly the input EZSL was producing genuinely had two unlocated/inconsistent outputs once Babylon's injection landed.

Fix: `src/integrations/babylon.ts`'s `addFragmentOutputLocation` post-processes the fragment source generated by `generateFragmentShaderMapped` (reused unmodified, `includeVersionDirective: false`, same as Three's usage) to rewrite `out vec4 fragColor;` into `layout(location = 0) out vec4 fragColor;` — a simple, targeted string replacement, scoped to this integration module only. `generateFragmentShaderMapped` itself was deliberately **not** changed — Three.js's integration and plain `mount()` have no equivalent output-collision detector in their host environments and don't need this qualifier; changing the shared generator would have been unnecessary blast radius for a Babylon-specific quirk. Regression-tested directly in `tests/babylonIntegration.test.ts`.

### 2. A silent black-screen bug: `setUniform`'s value shape, not the integration's fault

After the compile error was fixed, the example rendered — but as a solid black sphere with no visible color gradient at all, despite the fragment shader compiling and linking successfully and the vertex displacement visibly animating (confirmed by comparing two screenshots ~1s apart: the mesh's silhouette genuinely deformed between frames, proving the vertex stage was running).

Root cause: `examples/babylon-integration/main.ts` called `setUniform("resolution", [canvas.clientWidth, canvas.clientHeight])` — a **plain array**, exactly the same shape Three.js's own example (`examples/three-integration/main.ts`) passes for the identical call. This works for Three.js because its `setUniform` just assigns to `material.uniforms[glslName].value` with no shape validation or conversion at all. It does **not** work for Babylon: `dispatchBabylonUniform` routes a `vec2`-typed uniform to `material.setVector2(glslName, value)`, and Babylon's real `setVector2` expects a `{x, y}`-shaped value (or a `BABYLON.Vector2` instance) — a plain `[w, h]` array has no `.x`/`.y` properties, so `u_resolution` was silently set to `undefined`/garbage every frame, `uv` was computed from a broken `gl_FragCoord.xy / u_resolution` division, and the fragment shader's real output (a genuine `[uv.x, uv.y, pulse]` gradient — confirmed correct by direct compilation, see the code snippet in this doc's earlier sections) was masked by `NaN`/degenerate `uv` values that happened to render as solid black.

This is not a bug in `createBabylonMaterial`/`dispatchBabylonUniform` themselves — the dispatch logic correctly called `setVector2` for a `vec2`-typed uniform, exactly per its design. It's a real, confirmed instance of the exact structural difference this whole integration was built around: Babylon's typed-setter API expects real, shaped values, not Three.js's "hand it whatever and I'll mutate `.value`" model. Fixed by passing `{ x: canvas.clientWidth, y: canvas.clientHeight }` instead. Documented directly in the example's own code comment (`main.ts`) as a concrete, real gotcha for anyone porting Three.js-integration code to the Babylon integration, not just in this doc.

## Capability/limitation summary

- **No varyings** — a vertex program and its paired fragment program compile completely independently, same limitation as the Three.js integration; not attempted here either.
- **No vertex-stage `fn`/structs/arrays** — `VertexProgram` has no `topLevel` field, same as Three's integration.
- **No `normalMatrix`-equivalent** — confirmed absent from `ShaderMaterial`'s real auto-bind logic, not wired up; a normal-transformation matrix would need to be computed and set manually via `setMatrix3x3`, outside this integration's current scope.
- **No `setBool` dispatch** — confirmed absent from `BABYLON.ShaderMaterial`'s real method list; a `bool`-typed uniform routes through `setInt(0|1)` instead, Babylon's own real convention.
- **`vec2`/`vec3`/`vec4`/`mat2`/`mat3`/`mat4` dispatch branches are unreachable through a real, currently-compilable `.ezsl` source today** — EZSL's implicit-uniform inference always infers `float` on first reference (see `docs/architecture/type-system.md`; there is no mechanism to retroactively widen an inferred uniform's type from later usage), so no plain user-declared uniform can currently be anything but `float`/`int`/`bool` in practice. These dispatch branches are still real, correct, forward-looking logic — verified directly via `dispatchBabylonUniform`'s own dedicated unit tests (`tests/babylonIntegration.test.ts`) rather than left untested — ready for a future EZSL feature (e.g. explicit uniform type annotations) that could actually produce a non-float user uniform.
- **`sampler2D`/multi-pass buffer support is not exposed through `CreateBabylonMaterialOptions`** — no `bufferNames` option exists on this integration; `dispatchBabylonUniform`'s `sampler2D` → `setTexture` branch exists for completeness/forward-compatibility but is not reachable through `createBabylonMaterial`'s current public surface.

## Validated example

`examples/babylon-integration/` (`vertex.ezsl` + `fragment.ezsl`, wired via `createBabylonMaterial(BABYLON.ShaderMaterial, {...})`) displaces a sphere's vertices along their normals with a `sin(position.x * 4.0 + time * 2.0)` wave (amplitude modulated by `length(cameraPosition)` — demonstrating a real Babylon-specific builtin with no Three.js equivalent), and colors it with an animated `[uv.x, uv.y, pulse]` fragment gradient, directly comparable in spirit to Three's own icosahedron example. Confirmed in a real Chromium browser (via Playwright), across two screenshots ~1 second apart, after fixing both real bugs above: a visible red/green/blue gradient (proof the fragment shader is producing real, correct color, not the earlier black-screen failure), a visibly different silhouette between the two captures (proof the vertex displacement is actually running), and zero uncaught page errors. Run with `npm run example:babylon-integration`. The compile/mount smoke check (no screenshot comparison) is additionally exercised on every `npm run test:integration` run via a dedicated block in `examples/_harness/main.ts`, mirroring the existing `three-integration` block.
