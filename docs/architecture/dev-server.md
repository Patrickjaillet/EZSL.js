# EZSL.js — Live-Reload Dev Server (v0.7, part 2)

Internal design doc for the "Live-reload dev server (`ezsl dev`) with hot shader swapping (no full page reload)" item of v0.7.x "Developer Experience". Read `docs/architecture/cli.md` first (the `build`/`check`/`watch` CLI this extends) and `docs/architecture/transpiler-pipeline.md`'s runtime section (`mount()`).

**Scope note**: this is the second v0.7.x item built, after the CLI tool. The VS Code extension and browser-DevTools source-map support are separate, not-yet-started roadmap items.

## What "hot shader swapping" means here, concretely

`ezsl dev <file.ezsl>` starts a local HTTP server, serves a minimal auto-generated page with a fullscreen `<canvas>`, and — every time the watched `.ezsl` file changes on disk — recompiles it and pushes the result to the already-open browser tab, which updates the rendered shader **without reloading the page**. "No full page reload" is not just about avoiding a flash: reloading would tear down and recreate the WebGL2 context, canvas, and any accumulated GPU state, and would restart `time` from zero. The actual mechanism (an explicit user decision) is `EzslRuntimeHandle.swapProgram()`, a new method added to `mount()`'s returned handle (`src/runtime/bootstrap.ts`) that compiles and links a new program into the **same** WebGL2 context and switches the running `requestAnimationFrame` loop to render it from the next frame on — the canvas, context, and elapsed-time clock are untouched by a swap.

## Architecture: three new pieces

1. **`swapProgram()` on `mount()`'s handle** (`src/runtime/bootstrap.ts`) — the client-side primitive. Not new server/CLI code; a genuine addition to the browser runtime, usable independently of `ezsl dev` by anyone who wants hot-swapping (e.g. a hand-rolled editor).
2. **`runDev()`** (`src/cli/devServer.ts`) — a plain `node:http` server (no framework dependency) serving three routes: `/` (an auto-generated HTML page), `/client.js` (a small bundled client script), `/events` (a Server-Sent Events stream), plus a catch-all that serves the built library (`dist/`) statically so the client's `import { mount } from "/index.js"` resolves.
3. **`ezsl dev`** (`src/cli/index.ts`) — the CLI subcommand wiring, matching `build`/`check`/`watch`'s existing pattern (`--vertex`, plus a new `--port`).

## `swapProgram()`: why it exists instead of destroying and re-`mount()`-ing (explicit user decision)

Two ways to swap the running shader were considered. The rejected one: have the dev server's client script call `handle.stop()` then `mount()` again on the same canvas for every edit. This is simpler (zero changes to `bootstrap.ts`) but has two real costs: it re-acquires a WebGL2 context on the same canvas every single edit, and browsers cap the number of live WebGL contexts per page (typically 8–16) — a long editing session making dozens of edits risks silently losing the ability to acquire a new context partway through (the browser evicts the oldest context, or `getContext` starts returning `null`). It also discards whatever GPU-side state (if any existed) the old context held, and restarts `startTime`, so `time` jumps back to `0` on every edit — a visibly disruptive "shader restarted" flash even without a page reload.

**The chosen approach**: `swapProgram(newProgram, options)` compiles and links `newProgram` into the *existing* `WebGL2RenderingContext`, reusing the existing VAO/vertex buffer (the fullscreen quad geometry never changes between EZSL programs — only what fragment shader draws it does) and only re-fetching uniform/attribute locations against the newly linked program. This required refactoring `setupWebglRenderer` (`src/runtime/bootstrap.ts`, shared by `mount()` and `mountToCanvas2D()` since the v0.6 Canvas2D milestone) from a one-shot "compile once, return a renderer" function into one with an internal `linkAndBind()` step callable again later — `swapProgram` on the returned renderer just calls it again. `mount()`'s returned `EzslRuntimeHandle` now exposes `swapProgram` too (`mountToCanvas2D`'s handle does not — the dev server only targets `mount()`'s direct-to-canvas path; extending hot-swap to Canvas2D interop was out of scope for this milestone and would need its own design pass).

**A real subtlety found while building this**: `a_position`'s attribute location is not guaranteed to stay the same across two separately linked GLSL programs — the driver's linker is free to assign it differently even for byte-identical vertex shader source. An early version of `linkAndBind` reused the *first* program's `a_position` location for every subsequent swap; this happened to work in local testing (this environment's driver consistently assigns location 0), but is not something the WebGL spec guarantees, so `vertexAttribPointer`/`enableVertexAttribArray` are re-run against the *new* program's own queried location on every swap, not cached from the first link.

**On a failed swap** (a syntax error mid-edit), `swapProgram` throws via the same v0.4 translated-error path `mount()`'s initial compile uses, and — critically — leaves `glProgram`/the uniform locations untouched, so the *previous* program keeps rendering on the next frame. This was verified with a real, live edit cycle in a Chromium browser (not just by reading the code): editing a working shader to `color = unknownFn(1.0)` showed the previous frame's color underneath a red error overlay (the dev server client's own error-handling — see below), and editing back to valid source recovered cleanly with no leftover state from the broken attempt.

## Transport: Server-Sent Events, not WebSocket (explicit user decision)

The server only ever needs to push one kind of message to the browser — "here is the newly compiled program" (or an error) — never receive anything back. `EventSource`/SSE is a built-in browser API requiring zero client-side or server-side library code (a raw `text/event-stream` response with `data: <json>\n\n` lines, kept open, is all `/events` does — `src/cli/devServer.ts`'s `sseWrite`), consistent with the CLI's own zero-new-dependencies stance (`docs/architecture/cli.md`). A WebSocket was considered — closer to what Vite's own HMR uses — but rejected: it's bidirectional machinery for a channel this project only ever uses in one direction, and Node's `http` module has no built-in WebSocket server, so it would require either a dependency (`ws`) or hand-rolling the WebSocket handshake, neither of which buys anything here.

## The served page and client script

`pageHtml()` generates a minimal, self-contained HTML page: a fullscreen `<canvas id="ezsl-dev-canvas">`, a hidden `<pre id="ezsl-dev-error">` overlay (styled dark-red, monospace, only shown on a compile failure), and a `<script type="module" src="/client.js">`. `CLIENT_SCRIPT` (served verbatim as a string constant, not bundled from a separate file — there's exactly one small script and no build step needed for it) does the actual work: sizes the canvas to the window, connects an `EventSource` to `/events`, and on each message either calls `mount()` (the very first message) or `handle.swapProgram()` (every later one), showing the error overlay instead of touching the canvas when a message reports a compile failure — either an EZSL-side `CompileError`/`ParseError`/`LexError` (caught server-side, see below) or a WebGL-driver-side failure from `mount()`/`swapProgram()` itself (caught client-side, since only the browser has a real WebGL2 context to fail against).

## What gets pushed over SSE, and why it's simple

The compiled `Program`/`VertexProgram` a `.ezsl` file produces is already plain JSON-serializable data — `glsl` strings, `EzslType` strings, numbers, nested objects of the same (see `src/codegen/types.ts`; confirmed by round-tripping a real compile through `JSON.stringify`/`JSON.parse` while building this, and asserted directly in `tests/devServer.test.ts`). That's what keeps the server/client split this thin: the server does the *exact same* `compileEzsl`/`compileEzslVertex` call `build`/`check`/`watch` already make (`compileToMessage` in `devServer.ts`, sharing `formatCliError`/`isEzslPipelineError` from `docs/architecture/cli.md`'s CLI), JSON-serializes the result, and the client's `mount()`/`swapProgram()` accept that exact object shape directly — no separate wire format, no client-side compiler, no build step translating one representation into another.

## Testing without real sockets

`tests/devServer.test.ts`'s first version made real `node:http` client requests (and, briefly, `fetch`) against a `runDev`-started server listening on `port: 0`. This reliably **hung** — confirmed, with an isolated repro containing no EZSL code at all (a bare `http.createServer` + `http.request`), that Jest's `testEnvironment: "node"` sandbox has an incompatibility where a `node:http` client request's response never fires a `data` event. The identical server and client-reading logic worked correctly both in a plain `node script.mjs` run outside Jest and in a real Chromium browser via Playwright (see "Validated example" below) — so this is a Jest/VM-sandbox limitation in this environment, not a bug in the dev server.

The fix was to stop making real HTTP client requests inside unit tests at all: `createRequestListener()` (a new export, `src/cli/devServer.ts`) builds the `(req, res) => void` function `runDev` hands to `http.createServer`, taking its `sseClients`/`latestMessage` state as explicit parameters instead of closing over server-local variables — this makes it callable directly against small fake `req`/`res` objects (an `EventEmitter` with a `.url` property; a `writeHead`/`write`/`end`-recording fake response), in-process, with no socket at all. `compileToMessage()` (also newly exported) is tested the same way, directly, as plain async logic. `runDev()` itself is still tested as a real server (real `http.createServer`, a real OS-assigned port, a real `fs.watch` loop reacting to a real file edit) but only observed through its own process-level side effects (the `[ezsl dev] recompiled ...` stdout log line) or by re-deriving what it should have broadcast, never through a real client socket connection to it. This keeps the tests honest about exercising real code paths (the actual request listener, the actual file watcher) while sidestepping the one specific sandbox incompatibility.

## Validated example (real browser, not just unit tests)

Built and ran `ezsl dev` against a real temp `.ezsl` file, driven with Playwright against a real Chromium browser (not the integration-suite harness — a standalone script, since this dev server is new infrastructure outside `examples/`):

- Initial page load rendered the shader's starting color correctly (confirmed via screenshot).
- Editing the watched file on disk (three different color edits across the session) each produced a visually confirmed, correct hot-swap — new color, same page, no navigation between screenshots (verified by never calling `page.goto` a second time).
- Editing to a deliberately broken program (`color = unknownFn(1.0)`) showed the red error overlay with the exact same source-snippet-plus-caret format `ezsl build`/`check` produce (`formatCliError`, shared with the CLI), and the canvas kept showing its last-good frame underneath rather than going blank.
- Editing back to valid source recovered cleanly — overlay hidden, canvas updated, no residual state from the broken attempt.

This is the standard the project holds every runtime-facing feature to (see `docs/architecture/canvas2d-interop.md`, `docs/architecture/three-integration.md`) — a passing unit test suite alone was not treated as sufficient validation for this milestone.

## What this milestone does not implement

- **Hot-swap for `mountToCanvas2D`.** Only `mount()`'s handle gained `swapProgram`; the dev server only targets the direct-to-canvas path.
- **Multi-pass (`createPipeline`) or Three.js (`createThreeMaterial`) support in `ezsl dev`.** The dev server compiles and swaps a single fragment (or, with `--vertex`, vertex) program via plain `compileEzsl`/`compileEzslVertex` — not a multi-file pipeline or a Three.js scene. `ezsl build`/`check`/`watch` share this same single-file scope (see `docs/architecture/cli.md`).
- **Reconnection/multi-tab robustness beyond what `EventSource`'s own automatic-reconnect already provides.** Multiple browser tabs connecting to the same `/events` endpoint all receive the same broadcasts (the server doesn't special-case this), which happens to work but wasn't a deliberate design goal.
- **HTTPS, authentication, or any hardening beyond "this is a localhost developer tool."** The static-file route has no path-traversal guard beyond Node's own URL parsing — acceptable because it only ever serves this project's own already-public `dist/` output to `localhost`, never user-supplied paths (documented inline in `devServer.ts`).
- **A configurable/`package.json`-driven page template.** The HTML page and client script are fixed; there's no way to customize them from the CLI today (same open scope note as `docs/architecture/cli.md`'s "`package.json`-driven config" gap).

## Tests

`tests/devServer.test.ts` (17 cases): `compileToMessage` for fragment/vertex/success/failure/JSON-round-trip; `pageHtml`/`CLIENT_SCRIPT` content assertions; `createRequestListener` against fake `req`/`res` objects for all four routes (`/`, `/client.js`, `/events` with and without a pending message, SSE-client removal on request close, the `dist/`-serving fallback, and 404); `runDev`'s real server lifecycle (real listen, real `port: 0` resolution, real close, and a real `fs.watch`-triggered recompile observed via the recompile log line). All 17 pass; the full project suite is 403/403 after this change (was 386 after the CLI milestone). See "Testing without real sockets" above for why no test in this file makes a real HTTP client request.
