# EZSL.js — CLI Tool (v0.7, part 1)

Internal design doc for the "CLI tool (`ezsl build`, `ezsl watch`, `ezsl check`) with `package.json`-driven config" item of v0.7.x "Developer Experience". Read `docs/architecture/transpiler-pipeline.md` first (v0.1 core pipeline) — this doc covers a new *entry point* into that same pipeline, not a new compiler stage.

**Scope note**: this is the first v0.7.x item built. The VS Code extension, live-reload dev server, and browser-DevTools source-map support are separate, not-yet-started roadmap items and are not covered here.

## What the CLI is (and isn't)

`ezsl` is a thin Node.js entry point (`src/cli/index.ts`, `bin: { "ezsl": "./dist/cli/index.js" }` in `package.json`) over the pure `tokenize → parse → compile → codegen` pipeline that already exists (`compileEzsl`/`compileEzslVertex` + `generateFragmentShaderMapped`/`generateThreeVertexShaderMapped`). It does not add any new compiler capability — every `.ezsl` file the CLI can compile, `compileEzsl()` could already compile from a browser or test file. What's new is a command-line surface for that pipeline: `build` (compile to a `.glsl` file), `check` (compile and report pass/fail, no output file), `watch` (re-run `build` on every file change).

**No runtime/WebGL2 involvement of any kind.** `mount()`, `createPipeline()`, and `createThreeMaterial()` all require a real `canvas`/WebGL2 context and are unusable outside a browser. The CLI runs in plain Node.js with no browser and no GPU — so it can only ever exercise the pure-compile half of the pipeline. This is not a limitation to work around; it's the correct scope for a command-line compiler tool (the GLSL-to-driver link step is inherently a runtime concern, not a build-time one — see the "check: compilation-only" decision below).

## Command semantics (explicit user decisions)

Two scope questions were resolved before implementation, both by explicit user choice:

- **`ezsl build`'s output**: writes a `<name>.glsl` file next to the source `<name>.ezsl` (`glslOutputPath` in `src/cli/commands.ts`), rather than printing to stdout or emitting a structured JSON blob. This matches the project's own design pillar — "every EZSL construct must transpile to clean, inspectable, native GLSL, no opaque black-box output" (`CLAUDE.md`) — a real, readable, committable `.glsl` file *is* that pillar applied to the CLI. Stdout-only was rejected as less convenient for the common "commit the generated GLSL for inspection" workflow; a structured JSON output (GLSL + uniforms + source map) was judged over-engineered for what's needed today and can be added later without breaking `build`'s existing plain behavior.
- **`ezsl check`'s scope**: compilation only — `tokenize → parse → compile → codegen`, catching `LexError`/`ParseError`/`CompileError` (see below), never a real WebGL2 link. A real-link `check` was considered (it would additionally catch v0.4's driver-level ANGLE errors, e.g. a `glsl { ... }` Escape Hatch block using a reserved word — see `examples/error-demo/`, which `ezsl check` deliberately reports `OK` on, since that failure only manifests at real GLSL compile time) but rejected: it would require a headless WebGL2 context in Node (e.g. `headless-gl`, or spinning up Playwright per invocation), a meaningfully heavier dependency and startup cost for a command whose whole appeal is being fast and dependency-free. This is a real, documented scope boundary, not an oversight — verified directly: `node dist/cli/index.js check examples/error-demo/shader.ezsl` prints `OK` (exit 0), which is *correct* per this scope, not a bug.

## Error handling: three exception classes, one pretty-printer

The pure pipeline can only ever throw `LexError`, `ParseError`, or `CompileError` (`src/lexer/tokenizer.ts`, `src/parser/parser.ts`, `src/compiler/compile.ts` respectively) — all three already carry `line`/`column` and a formatted `.message`, but none of them are what `src/errors/printer.ts`'s `formatDiagnostic` formats: that function is v0.4's *driver*-diagnostic pretty-printer, consuming a `TranslatedDiagnostic` parsed from a real WebGL compile log, which the CLI never has (see above). `src/cli/formatCliError.ts` is a small, separate pretty-printer for these three EZSL-side exception classes — same visual language (source snippet + caret line + message), different input shape and different set of error classes, not a variant call path through the v0.4 dictionary/translation machinery (there is no driver text to translate; the message is already plain English straight from the compiler, e.g. `unknown function 'smoothstp' — did you mean 'smoothstep'?` for a real did-you-mean-demo run through the CLI). `isEzslPipelineError` narrows `unknown` to exactly these three classes so `compileSourceToGlsl` can catch-and-format them while rethrowing anything else (a real bug, not a user-facing compile error) rather than silently swallowing it.

## `watch`: file-polling, not a live-reload transport

`ezsl watch <file.ezsl>` builds once immediately, then uses `node:fs/promises`' `watch()` (an async iterator over filesystem change events) to rebuild on every subsequent change, printing a formatted error and **continuing to watch** rather than exiting on a compile failure — the entire point of watch mode is staying alive through edit mistakes. This is a plain file-system watch loop with no network/browser component: it does not push updates into an already-open browser tab, and is a genuinely different thing from the roadmap's separate, not-yet-built "Live-reload dev server (`ezsl dev`) with hot shader swapping (no full page reload)" item — that item implies a running dev server pushing updates into a live page (analogous to Vite's own HMR), which `ezsl watch` does not attempt. `ezsl watch`'s "hot shader swapping" is scoped to "the `.glsl` file on disk gets rewritten fast," which is a real, useful, and much smaller feature than a browser-side reload transport.

Verified with a real, live filesystem edit cycle (not just a unit test): started `ezsl watch` against a temp file, observed the initial build write a `.glsl` file, edited the source (`color = [1.0, 0.0, 0.0]` → `color = [0.0, 1.0, 0.0]`), observed a real rebuild with the new color reflected in the rewritten `.glsl` file, then edited to an intentionally-broken source (an unknown function call) and confirmed the loop printed a formatted error and kept running rather than exiting — the process was still alive and watching afterward. (Windows' `fs.watch` fired the `change` event twice for a single edit during this test — a known Node/Windows behavior, not an EZSL bug; harmless here since rebuilding identical content twice is idempotent.)

## `--vertex`: fragment vs. vertex stage

By default the CLI compiles fragment-stage EZSL (`compileEzsl` + `generateFragmentShaderMapped`). A `.ezsl` file authored for the v0.6 Three.js vertex stage (`position`/`normal`/camera-matrix builtins, required `glPosition` output — see `docs/architecture/three-integration.md`) needs `compileEzslVertex` + `generateThreeVertexShaderMapped` instead, which use a different builtin scope and a different required output-statement name. The CLI cannot infer which stage a file is from its content alone (both stages are plain `.ezsl` text with no header/pragma), so `--vertex` is an explicit flag on `build`/`check`/`watch`. Verified against the real `examples/three-integration/vertex.ezsl`: `ezsl build examples/three-integration/vertex.ezsl --vertex` produces real vertex-stage GLSL (`in vec3 position;`, `uniform mat4 modelViewMatrix;`, `gl_Position = ...`), confirming the flag actually routes through the vertex pipeline rather than just accepting the option and ignoring it.

## No new dependencies

Argument parsing (`src/cli/index.ts`'s `parseArgs`) is hand-written — three subcommands (`build`/`check`/`watch`), one boolean flag (`--vertex`), and `-h`/`--help` don't warrant a parsing library, and `ezsl` (the package) has zero production dependencies today; adding one for argument parsing alone was judged not worth the trade-off (explicit user decision). `watch` uses only `node:fs/promises`, part of the Node.js standard library.

## What this milestone does not implement

- **`package.json`-driven config.** The roadmap line item mentions this, but no config schema (e.g. an `"ezsl"` key in the consuming project's `package.json` listing default files/output directories) exists yet — every invocation takes its file path as an explicit CLI argument. Revisit if/when the CLI needs to compile more than one file per invocation (a glob-driven "build all `.ezsl` files in `src/shaders/`" mode is the natural next step that would motivate this).
- **A real WebGL2 link check.** See "`check`'s scope" above.
- **`ezsl dev` (the live-reload dev server).** A separate, not-yet-started roadmap item — see "watch: file-polling, not a live-reload transport" above for why it's a different feature, not a renamed version of `watch`.
- **Glob/multi-file input** (`ezsl build src/**/*.ezsl`). Each command currently takes exactly one file path.
- **Publishing to npm** — `bin` is wired up in `package.json` so the CLI would work as a global/`npx` command once published, but this milestone doesn't include an actual npm publish; `npm run cli -- <args>` (or `node dist/cli/index.js <args>` directly) is how it's invoked in this repo today.

## Tests

`tests/cli.test.ts` (13 cases): `compileSourceToGlsl` for both fragment and vertex stages, both success and `CompileError`/`ParseError` failure paths, and rethrowing of a non-pipeline error; `formatCliError`'s snippet/caret rendering including the out-of-range-line-number case; `isEzslPipelineError`'s narrowing; `runBuild`/`runCheck` against a real temp-directory filesystem (real file writes, real exit codes, confirming no `.glsl` file is written on a failed `build`/`check`). `watch` itself is intentionally not unit-tested (an indefinite async-iterator loop is a poor fit for Jest) — it was instead validated with a real, manual, live-edit run as described above, consistent with how this project validates runtime-loop behavior elsewhere (e.g. `mount()`'s `requestAnimationFrame` loop is validated via real browser screenshots, not a mocked timer).
